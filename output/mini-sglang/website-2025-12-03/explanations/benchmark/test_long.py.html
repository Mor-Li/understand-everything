benchmark/test_long.py

这份代码是一个性能测试（Benchmark）脚本。

简单来说，它的作用是：模拟一群用户同时向一个 AI 服务器发送非常长的文本（比如长篇小说），然后计算服务器处理得有多快，会不会崩掉。

为了让你彻底看懂，我把这段代码拆解成一个“任务清单” (To-Do List)，就像你作为测试员，一步一步执行任务一样。

📋 任务清单 (Task To-Do List)

  1. 准备工具箱：加载必要的库，准备好计算文本长度的尺子（Tokenizer）。
  2. 制定测试计划：决定要测试多长的文本（16k），以及一次并发多少个请求（Batch Size）。
  3. 准备“考题”：生成一堆很长的随机文本，准备发给 AI。
  4. 建立连接：尝试连接本地的 AI 服务器（端口 1919）。
  5. 试探一下（Ping）：在发送大量数据前，先发一条短消息测试服务器是不是活着的。
  6. 正式压测：把准备好的长文本一股脑发给服务器，并记录时间。
  7. 批改试卷：收集结果，计算速度（吞吐量）和延迟。

🧐 详细步骤讲解

下面我按照上面的清单，结合代码一步步给你讲：

Task 1: 准备工具箱 (Setup)

代码一开始导入了一堆包（asyncio, openai 等）。 最关键的是这一步：

model = MODEL_PATH
tokenizer = AutoTokenizer.from_pretrained(model)
  • 观点：在测试大模型之前，我们需要一把“尺子”来衡量数据量。在 AI 界，数据的单位是 Token（词元）。这里加载 Tokenizer 就是为了能准确生成指定长度（Token 数）的测试文本。

Task 2: 制定测试计划 (Config)

MAX_LENGTH = 16384  # 这是一个非常长的文本（约等于中文2-3万字）
TEST_BS = [16]      # Batch Size，表示一次性并发发过去 16 个请求
PORT = 1919         # 目标服务器的端口
  • 观点：这是一个针对长文本（Long Context）的压力测试。MAX_LENGTH 设得很大，专门用来测模型读长文会不会卡死或变慢。

Task 3: 准备“考题” (Generate Data)

代码里定义了一个函数 generate_task：

async def generate_task(max_bs: int) -> List[str]:
    # ...循环生成随机的长文本...
    message = generate_message(tokenizer, MAX_LENGTH)
    # ...
  • 观点：生成长文本是很耗时间的。这里用了一个技巧 asyncio.create_task(generate_task(...))（在后面的代码中调用），意思是让电脑在后台一边生成这些巨大的数据，一边往下执行别的任务，不傻等。

Task 4 & 5: 建立连接并试探 (Connect & Dry Run)

这是代码中最聪明的一段逻辑：

async with OpenAI(...) as client:  # 建立连接
    # 1. 启动后台任务：开始造那堆巨大的数据
    gen_task = asyncio.create_task(generate_task(max(TEST_BS)))

    # 2. 试探：造一个很短的消息 (100 tokens)
    test_msg = generate_message(tokenizer, 100)
    # 3. 发送试探：看服务器能不能回话
    test_result = await benchmark_one(client, test_msg, 1, model)
  • 观点：“先尝一口汤烫不烫”。
    • 如果直接把 16 个超长文本发过去，万一服务器没开，或者配置错了，程序会卡很久才报错。
    • 所以，先发一个短的（benchmark_one），如果服务器能正常回复（Server connection successful），再等待后台的长文本数据生成完毕（msgs = await gen_task），然后开始真正的测试。

Task 6: 正式压测 (Run Benchmark)

for batch_size in TEST_BS: # 这里就是 16
    # 发送请求！
    # msgs[:batch_size]: 取出16条长文本
    # 512: 要求模型针对每条文本生成 512 个字作为回答
    results = await benchmark_batch(client, msgs[:batch_size], 512, model)
    process_benchmark_results(results)
  • 观点：这是核心战场。benchmark_batch 会同时把 16 条长达 16k 的文本发给服务器，并要求服务器吐出 512 个 token。这会极大地占用显存和计算资源。

Task 7: 批改试卷 (Process Results)

process_benchmark_results(results)
  • 观点：测试完了得有结论。这个函数（虽然具体实现被隐藏在 minisgl 库里）通常会打印出：
    • Throughput (吞吐量)：服务器每秒能处理多少个 Token？
    • Latency (延迟)：服务器收到请求后，多久才吐出第一个字？

总结

这个脚本是一个针对长文本场景的并发压力测试工具。

它在问服务器：“嘿，如果我让 16 个人同时给你发几万字的小说，并让你写读后感，你能不能扛得住？处理速度是多少？”
