python/minisgl/engine/graph.py

这份代码的核心功能是利用 CUDA Graph（CUDA 图） 技术来加速大模型推理中的 Decode（解码/生成）阶段。

简单来说，通常 CPU 指挥 GPU 干活是一步一步来的（发射指令 -> GPU 执行 -> 返回），这会有 CPU 的调度开销。CUDA Graph 相当于把一整套 GPU 指令“录制”下来，下次 CPU 只要按一个按钮，GPU 就自动把这一整套动作做完，极大地减少了 CPU 的开销。

为了让你读懂，我把这个文件的逻辑拆解成一个 “任务清单 (Todo List)”，我们按照这个流程一步步看代码是怎么实现的。

任务清单 (Task List)

  1. 策略制定：决定我们要录制哪些规格（Batch Size）的图？
  2. 环境准备：分配显存，准备录制设备。
  3. 预热 (Warmup)：先假装录一次，把该申请的内存申请好。
  4. 正式录制 (Capture)：针对每个 Batch Size，实际运行一遍模型并录制下来。
  5. 运行时：凑整 (Padding)：当真实请求来了，把数量凑成录制过的规格。
  6. 运行时：回放 (Replay)：播放录制好的图，得到结果。

详细步骤讲解

Task 1: 策略制定 —— 决定录制哪些 Batch Size

代码对应函数： _determine_cuda_graph_bs

  • 背景：CUDA Graph 是静态的，输入数据的形状（Shape）必须固定。我们不可能为 1 到 256 的每个数字都录制一个图，那样显存会爆。
  • 代码逻辑：
    • 看显存够不够（free_memory）。如果是 H200 这种大卡（>80GB），最大 Batch Size 设为 256，否则设为 160。
    • 生成一个列表：[1, 2, 4, 8, 16, 24, 32, ...]。
    • 解释：我们只录制这些特定档位的图。如果来了 7 个请求，我们就用 8 的图；来了 3 个，就用 4 的图。

Task 2: 环境准备 —— 初始化

代码对应： GraphRunner.__init__ 的前半部分

  • 代码逻辑：
    • self.logits = torch.empty(...): 提前在 GPU 上申请一块地，用来存放模型输出的结果（Logits）。
    • attn_backend.init_capture_graph(...): 告诉注意力机制（Attention）后端，“我要开始录像了，你准备一下 KV Cache 的指针”。
    • torch.cuda.empty_cache(): 清理垃圾，确保录制时有最大显存可用。

Task 3: 预热 (Warmup) —— 跑通流程

代码对应： GraphRunner.__init__ 中的 warm up 部分

  • 代码逻辑： python # 创建一个临时的图 g = torch.cuda.CUDAGraph() # 假装跑一次 forward with torch.cuda.graph(g, stream=stream): self.logits[:] = model.forward() del g # 跑完就删
  • 为什么要这样做？：PyTorch 和 CUDA 在第一次运行时会分配很多内部的 buffer。如果不预热，这些动态分配动作会被录制进图里，导致后续运行时崩溃或显存错误。预热是为了让环境进入“稳定态”。

Task 4: 正式录制 (Capture) —— 核心循环

代码对应： GraphRunner.__init__ 中的 for bs in pbar: 循环

这是整个文件最核心的部分。

  • 流程：
    1. 遍历我们选定的 Batch Size 列表（比如 128, 64, ... 8, 4, 2, 1）。
    2. 造假数据：batch = Batch(reqs=[dummy_req] * bs, ...)。用“哑弹（dummy request）”填满 Batch，因为录制只关心形状（Shape），不关心内容。
    3. 开始录制： python with torch.cuda.graph(g, pool=pool, stream=stream): self.logits[:bs] = model.forward()
      • pool=pool: 关键点。所有的图（Graph）共享同一个显存池（Memory Pool）。这意味着 Batch Size 为 1 和 Batch Size 为 128 的图，它们中间产生的临时变量共用同一块显存，极大地节省了显存占用。
    4. 保存：graph_list.append((bs, g))。把录好的图存进字典 self.graph_map 里。

Task 5: 运行时：凑整 (Padding)

代码对应： pad_batch 方法

  • 场景：现在正在推理，用户来了 batch.size = 7 个请求。
  • 问题：我们只有 1, 2, 4, 8... 的图，没有 7 的图。
  • 代码逻辑：
    • 在 self.graph_bs_list 里找，找到第一个比 7 大的数，也就是 8。
    • batch.padded_reqs = ... + [self.dummy_req] * (8 - 7)。
    • 操作：在原本的 7 个请求后面，塞进去 1 个假的请求（Dummy），凑成 8 个。

Task 6: 运行时：回放 (Replay)

代码对应： replay 方法

  • 场景：已经凑整好了，现在是 8 个请求（7真1假）。
  • 代码逻辑：
    • g = self.graph_map[batch.padded_size]：拿出 Batch Size = 8 的那个录像带（Graph）。
    • self.attn_backend.prepare_for_replay(batch)：更新一下指针，告诉图这次处理的数据实际地址在哪里。
    • g.replay()：播放录像。这一步非常快，CPU 几乎不干活，全扔给 GPU。
    • return self.logits[: batch.size]：虽然 GPU 算了 8 个结果，但我们只把前 7 个（真实的）结果切片返回去，丢掉那个假的。

总结

这个 graph.py 就像是一个 “GPU 动作预设管理器”： 1. 它先算好几种固定的队伍长度（1, 2, 4, 8...）。 2. 让模型排练每种长度的动作，并录下来。 3. 真正干活时，如果队伍长度不标准（比如 7），就塞几个假人凑成标准长度（8）。 4. 直接播放录像，让 GPU 极速干完活。

注意事项： * 代码里有个 can_use_cuda_graph 检查：只在 Decode 阶段（batch.is_decode）且 Batch Size 不太大时使用。因为 Prefill 阶段（处理长文本输入）计算量大且形状太动态，不适合用 Graph。
