python/minisgl/server/launch.py

这份代码文件 launch.py 其实就是整个 MiniSGL 系统的“总启动器”。它的作用就像是一个工厂的开工电闸。

为了让你更容易理解，我把这个代码执行的过程想象成开一家餐厅（AI推理服务）。下面是一个按时间顺序排列的 Task Todo List（任务清单），系统会一步步勾选这些任务来完成启动。

📋 任务清单：启动 MiniSGL 服务

Task 1: 阅读“开店指南” (解析参数)

  • 代码位置: launch_server 函数开头 -> parse_args(sys.argv[1:], run_shell)
  • 在干什么: 系统首先看你输入的命令（比如 python launch.py --model llama3 --port 8000）。它需要弄清楚：
    • 我们要加载哪个模型？
    • 用几张显卡（TP size）？
    • 监听哪个端口？
  • 观点: 一切始于配置。没有配置，系统不知道该干嘛。

Task 2: 制定“招工计划” (定义 start_subprocess)

  • 代码位置: launch_server 函数内部定义的 def start_subprocess(): ...
  • 在干什么: 这里并没有立刻启动进程，而是写好了一份“计划书”。这份计划书规定了需要招聘哪些后台工人（子进程）来干活。
    • 工人A (Scheduler): 负责控制显卡进行计算（这是最核心的大脑）。
    • 工人B (Detokenizer): 负责把模型算出的数字转回成文字（解码）。
    • 工人C (Tokenizer): 负责把用户输入的文字转成数字（编码）。
  • 观点: Python 的 GIL 锁限制了多线程性能，所以 AI 推理通常使用 多进程 (Multiprocessing)。这里准备用 spawn 方式启动多个独立的进程。

Task 3: 启动“前台接待” (运行 API Server)

  • 代码位置: launch_server 函数末尾 -> run_api_server(..., start_subprocess, ...)
  • 在干什么: 系统先启动 Web 服务器（比如 FastAPI），这就是餐厅的“前台”，准备接收用户的 HTTP 请求。
    • 关键点: run_api_server 内部会调用我们在 Task 2 中制定的 start_subprocess 计划。也就是说，前台就位后，才开始呼叫后台厨师就位。

Task 4: 执行招工，后台各就各位 (启动子进程)

  • 代码位置: start_subprocess 函数内部
  • 在干什么: 现在真正开始创建进程了（mp.Process(...).start()）。
    1. 启动 Scheduler (调度器):
      • 如果有 4 张显卡，就会启动 4 个 Scheduler 进程，每个对应一张卡（minisgl-TP{i}-scheduler）。
    2. 启动 De-tokenizer (解码器):
      • 启动 1 个进程专门处理输出文本。
    3. 启动 Tokenizer (编码器):
      • 启动 N 个进程处理输入文本（根据 server_args.num_tokenizer 决定）。

Task 5: 全员点名确认 (ACK Queue 同步)

  • 代码位置: ack_queue.get() 和 ack_queue.put("Scheduler is ready")
  • 在干什么: 这是一个非常重要的同步机制。
    • 主进程（前台）创建了一个队列 ack_queue。
    • 它会卡在这里死等（ack_queue.get()），直到所有子进程（Scheduler, Tokenizer 等）都加载完模型，并往队列里发送一句 "I'm ready"。
    • 只有收到 Scheduler + Tokenizers + Detokenizer 所有人的确认，系统才会打印 "Ready"，正式对外服务。
    • 观点: 防止模型还没加载进显存，用户的请求就进来了，导致报错。这叫“优雅启动”。

Task 6: 核心大脑开始运转 (Scheduler 逻辑)

  • 代码位置: _run_scheduler 函数
  • 在干什么: 这是显卡进程（Scheduler）内部执行的逻辑：
    1. import torch: 导入 PyTorch。
    2. Scheduler(args): 加载模型权重到 GPU。
    3. scheduler.sync_all_ranks(): 如果有多张显卡，大家对个表，确保步调一致。
    4. ack_queue.put(...): 告诉主进程“我准备好了”。
    5. scheduler.run_forever(): 进入死循环。
      • 这个死循环会不断检查有没有新的推理请求进来，有就算，没有就等。

总结一下这段代码的逻辑架构

这个文件其实构建了一个 "1 + N" 的架构：

  1. 1 个主进程 (API Server):

    • 负责和用户说话（HTTP 请求）。
    • 负责管理所有子进程的生杀大权。

  2. N 个后台子进程 (Workers):

    • Scheduler 进程: 扛着沉重的模型（显存），负责最繁重的矩阵计算。
    • Tokenizer 进程: 负责文本处理的脏活累活。

为什么你看不懂？ 因为它混合了 Web服务启动 和 多进程管理。 最核心的一行代码其实是 mp.Process(target=_run_scheduler, ...).start()，这行代码把 _run_scheduler 这个函数扔到了另一个独立的进程里去跑，让它在那边独自控制显卡，不干扰主进程处理网络请求。
