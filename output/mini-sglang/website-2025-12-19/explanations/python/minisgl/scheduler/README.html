python/minisgl/scheduler

这里是 python/minisgl/scheduler 目录的“导游手册”。

如果把整个大模型推理系统比作一家“火爆的高级餐厅”（GPU 是后厨，显存是座位），那么这个文件夹就是“餐厅经理办公室”。

1. 🏢 这个文件夹主要负责什么？

一句话总结：它负责“拼桌”和“翻台”。

显卡（GPU）非常昂贵，就像米其林大厨，不能让他闲着，也不能让他一次只炒一盘菜。 这个文件夹里的代码负责： 1. 接单：接收外面涌进来的用户请求。 2. 排班：决定下一秒钟，是让新来的客人点菜（Prefill），还是给正在吃的客人上下一道菜（Decode）。 3. 拼单：把好几个客人的需求打包在一起（Batch），扔给后厨一次性做完。 4. 管座：精打细算地分配显存（KV Cache），确保座位坐得满，但又不爆满。

2. 📄 各个文件的分工（餐厅岗位表）

为了让你秒懂，我们给每个文件分配一个餐厅里的角色：

  • scheduler.py —— 餐厅大堂经理（总指挥）

    • 作用：他是这里的老大。他不断地循环查看：“有没有新客人？后厨做完了吗？内存够不够？”。他协调下面所有的部门，驱动整个系统运转。

  • config.py —— 餐厅运营守则

    • 作用：一本死板的规则书。写着：“本店最大容纳多少人”、“每桌限时多久”、“通讯频道是多少”。经理干活全得照着这个来。

  • prefill.py —— 迎宾领位员（负责新客人）

    • 作用：专门处理刚进店的客人（新请求）。因为新客人要一次性读完很长的菜单（Prompt），计算量大。领位员要计算：“现在的空位够不够这位客人坐？如果不够，是不是要把他拆成两次接待（Chunking）？”

  • decode.py —— 传菜员（负责老客人）

    • 作用：专门照顾正在吃的客人（正在生成中的请求）。这些客人每次只吃一口（生成一个字）。传菜员负责把所有等着吃下一口的客人集合起来，催后厨赶紧出菜。

  • cache.py —— 仓库管理员（记性很好）

    • 作用：负责管理显存页（Page）。他最厉害的是有“记忆”（Radix Attention）。如果新客人点的菜以前有人点过（比如相同的系统提示词），他能直接从仓库里翻出以前的半成品，省去后厨重新做的时间。

  • table.py —— 座位排号员（记性一般）

    • 作用：比仓库管理员更底层。他只管手里有几张空桌子（Slot ID），来一个人发一个号，走一个人收回一个号。

  • io.py —— 对讲机系统

    • 作用：负责通讯。经理不直接进厨房，而是通过这个模块，用广播（Broadcast）的方式告诉所有显卡（Rank 0, Rank 1...）：“大家注意，这批任务来了，动作要整齐划一！”

  • utils.py —— 点菜/单据模板

    • 作用：这里不干活，只定义格式。规定了“点菜单（Request）”上必须写名字、菜名，规定了“派工单（Batch）”长什么样。

  • decode.py (补充)：

    • 注意：这里还有一个专门针对解码阶段的逻辑封装，配合 scheduler.py 使用。

  • __init__.py —— 办公室前台

    • 作用：把经理（Scheduler）和规则书（Config）摆在门口，方便外面的人直接找他们办事，不用进屋乱翻。

3. 📁 子文件夹的作用

(注：根据你提供的列表，当前目录下没有子文件夹，所有文件都是平铺的。这意味着这里就是调度逻辑的最底层，没有更深的分层了。)

4. 🧠 高层认知（快速理解）

要理解这部分代码，你只需要记住一个核心冲突：

GPU 算得太快，但显存太小。

这个文件夹里的所有代码，都在玩一个“俄罗斯方块”的游戏： * 形状是用户的请求（有的长，有的短）。 * 容器是有限的显存。 * 目标是塞得越满越好（吞吐量高），消除得越快越好（延迟低），绝对不能溢出（OOM）。

scheduler 就是那个玩俄罗斯方块的高手。
