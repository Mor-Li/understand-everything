python/minisgl/scheduler/prefill.py

这份代码是 minisgl（一个轻量级的大模型推理框架）中负责 Prefill（预填充） 阶段的调度器逻辑。

为了让你看懂，我们先把“代码”放一边，建立一个任务清单（Task List）。我们将整个流程想象成一家由于显存（座位）有限，必须精打细算的“大模型餐厅”。

“Prefill”阶段就是客人刚进店点菜（输入Prompt），厨师需要先理解完所有菜单（计算KV Cache），才能开始上菜（生成Token）。

下面是你的学习 Task List：

Task 1: 理解核心概念（基本术语）

目标： 搞懂我们在调度什么。

  1. Prefill (预填充): 大模型推理的第一步。把用户的输入（Prompt）一次性算完，生成 KV Cache。这一步计算量大，显存占用增长快。
  2. KV Cache: 大模型的“记忆”。算过的 Token 不需要重算，存下来就行。
  3. Token Budget (计算预算): 显卡一次能处理的 Token 数量是有限的（比如一次只能算 4096 个），不能撑死。
  4. Chunked Prefill (分块预填充): 如果用户的 Prompt 特别长（比如 1万字），一次算不完，就切成几段（Chunk）分批算。

Task 2: 认识“餐厅经理” (PrefillManager)

目标： 看懂代码最下面的 PrefillManager 类。

角色： 它是总调度，负责接待排队的客人（Request），并决定下一批谁能进厨房。

  • pending_list: 等位区。新来的请求 (add_one_req) 都先丢到这里排队。
  • schedule_next_batch (核心方法): 这是经理的主要工作。
    1. 它看了一眼厨房现在的能力 (prefill_budget)。
    2. 它叫来一个助手 PrefillAdder（专门负责算账的）。
    3. 它遍历排队的人 (pending_list)，一个个问助手：“这个能塞进去吗？”
    4. 如果助手说“能”，就放进 reqs 列表。
    5. 如果遇到一个超长的请求被“切分”了 (ChunkedReq)，就把剩下的部分留回排队列表头 (chunked_list)，下次接着算。
    6. 最后打包成一个 Batch 发给 GPU 去跑。

Task 3: 认识“算账助手” (PrefillAdder)

目标： 看懂 PrefillAdder 类。

角色： 它的工作是拿着计算器，精细计算每一个请求能不能塞进当前的显存和计算预算里。

它有两个核心变量： * token_budget: 还剩多少计算力（还能处理多少个 Token）。 * reserved_size: 预留显存大小（防止生成过程中显存爆了）。

它有两个核心动作（方法），我们一步步看：

Step 3.1: 尝试分配资源 (_try_allocate_one)

这是在问：“显存够不够存放这个人的记忆？”

  1. 查表 (cache_manager.match_req): 这一步很关键。它会看这个请求是不是以前来过（或者有一部分前缀是一样的，比如系统提示词）。如果以前算过，直接复用（Radix Attention 机制），省显存。
  2. 估算显存:
    • cached_len: 以前算过多少。
    • extend_len: 这次要新算多少。
    • estimated_len: 算完后总共占多少。
  3. 检查容量: 如果 estimated_len + reserved_size 超过了总显存 (available_size)，那就拒绝 (return None)。
  4. 分配物理内存: 如果够，就去 table_manager 申请物理显存位置，并把已有的缓存数据拷过去。

Step 3.2: 真正塞入请求 (_add_one_req)

这是在问：“这次预算能吃几口？”

  1. 计算切分:
    • remain_len: 还有多少字没读完。
    • chunk_size: 取 token_budget 和 remain_len 的最小值。
    • 关键点: 如果预算不够读完剩下的字，就标记为 is_chunked（分块）。
  2. 扣除预算: self.token_budget -= chunk_size。
  3. 搬运数据: 把用户输入的 Token ID (input_ids) 拷贝到 GPU 的显存池 (token_pool) 里。
  4. 生成对象:
    • 如果是分块的，返回 ChunkedReq（告诉经理：我还没完，下次继续）。
    • 如果读完了，返回普通的 Req（告诉经理：这人进入 Decode 生成阶段了）。

Task 4: 串联整个逻辑（代码走读）

现在回到 PrefillManager.schedule_next_batch 方法，逻辑就通了：

  1. 初始化助手: 创建 PrefillAdder，给它当前的预算。
  2. 循环处理排队者: for pending_req in self.pending_list:
  3. 尝试添加: 调用 adder.try_add_one(pending_req)。
    • 情况 A (老熟人继续吃): 如果这个请求本身就是上次没吃完的 (chunked_req)，直接继续喂 (_add_one_req)。
    • 情况 B (新客人): 先看显存够不够 (_try_allocate_one)，够的话再喂 (_add_one_req)。
    • 情况 C (没资源了): 返回 None，循环 break，这一批次这就样了。
  4. 处理结果:
    • 如果是 ChunkedReq（没读完），把它放回队首 (chunked_list)，保证下次优先处理它。
    • 如果是普通 Req，放入本批次执行列表。
  5. 发车: 返回 Batch 对象。

Task 5: 总结

这代码到底在讲啥？

它在实现一个支持“断点续传”和“缓存复用”的排队系统。

  • 为了省显存：它在 _try_allocate_one 里拼命找能不能复用之前的缓存 (match_req)。
  • 为了不卡顿：它引入了 ChunkedReq。如果一个 Prompt 太长，它不会让 GPU 一直卡在那算这一个人的，而是切成小块，每次算一点，利用 token_budget 控制每一轮的负载均衡。

现在你再回头看代码，重点关注 ChunkedReq（分块请求）和 PrefillAdder（资源计算器），应该就能看懂了。
