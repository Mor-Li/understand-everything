python/minisgl/server/launch.py

这份代码确实涉及到了多进程编程、分布式系统和深度学习推理服务的启动流程，乍一看很乱是很正常的。

你可以把这个脚本想象成一个 “餐厅经理”（Launcher）。它的工作不是亲自做菜，而是负责早上开门时，把前台（API Server）、后厨（Scheduler/GPU模型）和传菜员（Tokenizer）全部叫醒，并确保他们都准备好了再开始营业。

为了让你听懂，我把这个脚本的任务拆解成一个 TODO List，我们一步一步来看它是怎么把整个服务拉起来的。

🚀 启动流程 TODO List

  1. 准备阶段：读取“菜单”和“排班表”（解析命令行参数）。
  2. 定义核心任务：规定“后厨”（模型调度器）具体该干什么。
  3. 组建团队（核心逻辑）：
    • 招募“后厨团队”（启动 GPU 模型进程）。
    • 招募“翻译团队”（启动分词/反分词进程）。
    • 点名确认（等待所有进程发送“就绪”信号）。
  4. 正式开业：启动 HTTP 服务器，对外提供服务。

逐步讲解

Task 1: 准备阶段 (解析参数)

在代码的最下面 launch_server 函数的开头：

server_args = parse_args(sys.argv[1:])
logger = init_logger(__name__, "initializer")
  • 做什么：脚本运行的第一件事，是看用户输入了什么参数（比如模型路径在哪里、用几张显卡 tp_info.size、端口号是多少）。
  • 观点：任何服务启动前必须先拿到配置信息。

Task 2: 定义核心任务 (模型调度器逻辑)

看代码上方的 _run_scheduler 函数：

def _run_scheduler(args: ServerArgs, ack_queue: mp.Queue[str]) -> None:
    # ... 省略 import ...
    with torch.inference_mode():
        scheduler = Scheduler(config=args) # 初始化调度器
        scheduler.sync_all_ranks()         # 多显卡之间同步状态

        if args.tp_info.is_primary():      # 如果是主卡（0号卡）
            ack_queue.put("Scheduler is ready") # 发个信号：我准备好了！

        try:
            scheduler.run_forever()        # 死循环：一直等待并处理推理请求
        except KeyboardInterrupt:
            # ... 优雅退出 ...
  • 做什么：这是定义每一个 GPU 进程具体要干的活。它加载模型，同步状态，然后进入一个死循环（run_forever），不停地从队列里拿数据进行计算。
  • 观点：这是“后厨”的核心工作手册。注意那个 ack_queue.put(...)，这是为了告诉经理“我准备好了”。

Task 3: 组建团队 (启动子进程)

这是最复杂的部分，在 start_subprocess 函数里。因为 Python 有全局解释器锁（GIL），为了利用多核 CPU 和多张显卡，必须使用 multiprocessing (mp) 启动多个独立的进程。

3.1 设置启动方式

mp.set_start_method("spawn", force=True)
ack_queue: mp.Queue[str] = mp.Queue() # 创建一个消息队列，用来接收“就绪”信号
  • 观点：在 PyTorch/CUDA 编程中，必须用 spawn 方式启动进程，否则会报错。

3.2 启动 GPU 模型进程 (Scheduler)

world_size = server_args.tp_info.size # 比如你有 4 张卡，这里就是 4
for i in range(world_size):
    # ... 配置当前进程是第几号卡 ...
    mp.Process(
        target=_run_scheduler, # 让这个进程去执行 Task 2 定义的函数
        args=(new_args, ack_queue),
        daemon=False,
    ).start()
  • 做什么：如果你有 4 张显卡，这里就会循环 4 次，启动 4 个进程。每个进程负责管理一张显卡。

3.3 启动分词与反分词进程 (Tokenizer) 模型只认识数字，不认识中文/英文。所以需要专门的进程负责翻译。

# 启动 1 个反分词进程 (数字 -> 文本)
mp.Process(target=tokenize_worker, kwargs={... "tokenizer_id": num_tokenizers ...}).start()

# 启动 N 个分词进程 (文本 -> 数字)
for i in range(num_tokenizers):
    mp.Process(target=tokenize_worker, kwargs={... "tokenizer_id": i ...}).start()
  • 观点：分词（Tokenizer）是 CPU 密集型任务，为了不拖累 GPU 推理的速度，通常把它们单独放到另外的进程里跑。这里启动了 1 个负责输出的（DeTokenizer）和 N 个负责输入的。

3.4 点名确认 (同步)

# 1 scheduler + num_tokenizers + 1 detokenizer
for _ in range(num_tokenizers + 2):
    logger.info(ack_queue.get())
  • 做什么：主进程在这里卡住（阻塞），等待 ack_queue 里弹出消息。
  • 为什么：必须确保后台的所有进程（模型、分词器）都初始化完毕了，才能让 HTTP 服务器开张。否则用户发请求过来，后台还没准备好，就会报错。这里等待的数量 = 1个主模型信号 + N个分词器 + 1个反分词器。

Task 4: 正式开业 (启动 API Server)

代码的最后一行：

run_api_server(server_args, start_subprocess)
  • 做什么：
    1. 这一步启动了基于 Web 框架（比如 FastAPI 或其它）的 HTTP 服务器。
    2. 它把 start_subprocess 这个函数作为一个参数传进去了。
    3. 逻辑顺序：API Server 启动 -> 在内部调用 start_subprocess() -> 等待后台进程全部就绪 -> API Server 开始监听端口，接收用户请求。

总结：这段代码到底在讲啥？

这段代码是一个 Orchestrator（编排者）。

如果不写这个脚本，你需要手动开好几个终端窗口：一个运行模型，一个运行分词器，一个运行 Web 服务，还得自己掐表看它们什么时候启动好。

launch.py 帮你自动化了这一切： 1. 它作为主入口。 2. 它分裂出多个子进程去分别控制 GPU 和 CPU 处理数据。 3. 它利用 Queue 机制确保所有子进程都 Ready 了。 4. 最后它启动 Web 接口，让用户可以发请求进来。
