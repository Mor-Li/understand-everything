python/minisgl/config/context.py

这份代码是 minisgl（看起来是一个迷你版的大语言模型推理框架，类似 vLLM 或 SGLang）的核心状态管理模块。

它主要解决的问题是：当大模型同时服务多个用户时，如何管理每个用户的请求数据、如何把它们打包成批次（Batch）、以及如何告诉 GPU 当前要处理哪些数据。

为了让你听懂，我制定了一个四步走的学习清单 (Task List)。我们会从最微观的“单个请求”开始，一直讲到“全局管理”。

📚 学习清单 (Task List)

  1. Task 01: 理解最小单元 Req (Request)
    • 搞懂一个用户的请求里包含了哪些核心数据（输入、历史记录、显存位置）。
  2. Task 02: 理解打包机制 Batch & Phase
    • 搞懂为什么要区分 "Prefill" (预填充) 和 "Decode" (解码) 阶段。
    • 代码是如何自动判断当前处于哪个阶段的。
  3. Task 03: 理解环境上下文 Context
    • 搞懂什么是 page_table（页表），它在显存管理里起什么作用。
    • Context 类是如何作为“管家”协调 KV Cache 和 Attention 后端的。
  4. Task 04: 全局单例模式
    • 最后看一眼代码底部的 _GLOBAL_CTX 是干嘛的。

🚀 逐步讲解

Task 01: 理解最小单元 Req (Request)

概念： 想象你在跟 ChatGPT 聊天。你发出的每一次对话，在系统里就是一个 Req 对象。

代码核心点解析：

  • input_ids: 用户输入的文字转换成的数字 ID。代码里有一段逻辑 if not input_ids.is_cuda...，这是为了把数据从 CPU 搬运到 GPU 上，这是深度学习推理的第一步。
  • page_table_idx: 这是最关键的概念。 大模型推理需要记住之前的对话（KV Cache）。为了不浪费显存，现代框架（如 vLLM）使用“分页内存管理”。这个 ID 就是告诉你：“这个请求的历史记忆存储在显存的第几页”。
  • cached_len vs device_len:
    • device_len: 当前 GPU 上总共有多少个 token。
    • cached_len: 已经计算过并存入 KV Cache 的 token 数量。
    • 例子: 你发了 "Hello world" (2个词)。第一次处理时，device_len=2，cached_len=0。处理完后，这两个词存入缓存。当你生成下一个词时，cached_len 就变成 2 了。
  • append 方法: 当模型吐出一个新词（next_token）时，把它拼接到 device_ids 后面，并更新缓存长度。这就是“自回归生成”（一个词接一个词蹦）。

Task 02: 理解打包机制 Batch & Phase

概念： GPU 很强大，一次只处理一个人的请求太浪费了。我们需要把多个 Req 打包成一个 Batch 一起送进 GPU。

代码核心点解析：

  • Phase (阶段): 大模型推理主要分两个阶段：
    1. Prefill (预填充): 处理用户刚发的长提示词（Prompt）。这是一次性计算很多 Token，计算量大。
    2. Decode (解码): 根据提示词，一个接一个地生成新 Token。这是串行的，每次只处理 1 个 Token。
  • _auto_phase (自动判断阶段):
    • 代码逻辑：if all(req.extend_len == 1 for req in reqs): return "decode"
    • 解释: 如果这个批次里，所有请求都只需要处理 1个 新 Token（说明之前的都处理完了，正在生成新词），那就是 Decode 阶段。否则，只要有一个请求需要处理一大段新话，系统就认为是 Prefill 阶段。
  • Batch 类: 它就是一个容器，装着一堆 Req，并且标记了当前这堆东西是处于 Prefill 还是 Decode 状态。

Task 03: 理解环境上下文 Context

概念： Context 是整个推理引擎的“大管家”或者“工作台”。它持有所有共享的资源。

代码核心点解析：

  • page_table (页表):
    • 代码：create_page_table 创建了一个全是 0 的二维 Tensor。
    • 解释: 这是一个映射表。就像书的目录。它记录了“逻辑上的 Token”到底存放在“物理显存（KV Cache）”的哪个位置。
    • max_entries 是最大并发请求数，max_seq_len 是最大句子长度。
  • kv_cache & attn_backend:
    • kv_cache: 实际存放数据的仓库对象。
    • attn_backend: 实际执行 Attention 计算（比如 FlashAttention）的算法后端。
  • forward_batch (上下文管理器):
    • 这是一个 Python 的 with 语法糖。
    • 作用: 当模型开始跑一次前向传播（Forward）时，要把当前的 Batch 设为全局可见。
    • 流程：set_batch (设置当前批次) -> yield (执行模型计算) -> reset_batch (清空，准备下一轮)。

Task 04: 全局单例模式

代码：

_GLOBAL_CTX: Context | None = None
def set_global_ctx(ctx: Context): ...
def get_global_ctx() -> Context: ...

解释： 这是一个典型的编程模式。因为 Context 包含了页表、KV Cache 等核心资源，这些资源在模型的很多深层函数里都需要用到。 如果每次调用函数都把 ctx 作为一个参数传进去（比如 func(a, b, c, ctx)），代码会变得非常丑陋且麻烦。 所以，这里设置了一个全局变量。初始化一次后，任何地方只要调用 get_global_ctx() 就能拿到这个大管家，获取显存信息或当前批次信息。

总结

这段代码描述了一个 支持分页显存管理的大模型推理引擎的基础架构：

  1. Req: 记录单个用户的输入和缓存进度。
  2. Batch: 把多个 Req 凑在一起，并判断是该“阅读全文”(Prefill) 还是 “蹦字”(Decode)。
  3. Context: 拿着显存地图 (Page Table) 和仓库 (KV Cache)，指挥 GPU 处理当前的 Batch。
