python/minisgl/config

这里是 python/minisgl/config 目录的 README 文档。

1. 📁 这个目录主要负责什么？

如果把整个 minisgl 框架比作一个繁忙的 “大饭店”，那么 config 目录就是饭店的 “前台调度中心”。

它不负责具体的炒菜（计算）工作，也不负责种菜（模型定义），它的核心职责是：记账和派单。

它负责记录每一位客人的需求（Request），把客人的需求凑成一桌（Batch），并告诉后厨（GPU）哪桌客人坐在哪里（显存地址），以及这一桌是刚点完菜在等第一口（Prefill），还是已经在吃需要加菜（Decode）。

2. 📄 目录下直接文件的作用

根据提供的目录结构，这里只有一个核心文件：

context.py —— 饭店的大管家与账本

这个文件定义了推理引擎运行时的所有“状态信息”。它是连接“用户输入”和“底层硬件”的桥梁。

你可以把它拆解为三个层级来理解：

  • Req (Request / 订单)：
    • 作用：代表单个用户的请求。
    • 比喻：这是一张单人点菜单。上面写着客人说了什么话（input_ids），以及这位客人之前的对话记录被存在了仓库的哪个柜子里（page_table_idx）。
  • Batch (批次 / 托盘)：
    • 作用：代表一组同时送往 GPU 处理的请求。
    • 比喻：这是一个上菜的托盘。服务员不会为了一个饺子跑一趟厨房，而是把好几桌的单子凑在一起（Batching）。这个类还会自动判断当前这一托盘主要是为了“读长文章”（Prefill 阶段）还是“蹦新单词”（Decode 阶段）。
  • Context (上下文 / 调度总管)：
    • 作用：全局单例对象，持有显存页表、KV Cache 引用和当前批次信息。
    • 比喻：这是饭店的大堂经理。他手里拿着一本最重要的 “座位表” (page_table)，清楚地知道显存里哪一块空着，哪一块属于谁。所有具体的计算函数在干活前，都得先问问这位经理：“我现在该处理谁的数据？数据在哪？”

4. 🧠 高层认知：一句话理解它

python/minisgl/config 是整个系统的“状态容器”。

它不产生数据，也不计算数据，它负责组织数据。它解决了大模型推理中最麻烦的问题：如何在 GPU 只有一张嘴的情况下，有序地、高效地喂饱成百上千个同时说话的用户。
