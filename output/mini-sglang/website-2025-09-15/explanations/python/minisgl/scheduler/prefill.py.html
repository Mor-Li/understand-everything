python/minisgl/scheduler/prefill.py

这段代码实现了一个 PrefillManager（预填充管理器）。

在 LLM（大语言模型）推理中，"Prefill" 指的是处理用户输入的 Prompt（提示词）的阶段。这个阶段通常计算量很大，需要一次性算很多 Token。

为了让你看懂，我们可以把这个 PrefillManager 想象成一个 “餐厅领班”。他的工作是看着门口排队的顾客（Requests），根据餐厅现在的空桌子（显存 Cache）和厨师的忙碌程度（计算预算 Budget），决定让谁进来吃饭。

下面我列一个 Task Todo List，带你一步步走完这个领班的工作流程。

📋 领班的工作清单 (Task Todo List)

1. 准备工作 (初始化)

  • 代码位置: __init__
  • 任务: 上岗打卡，认识一下另外三个部门的经理。
    • cache_manager: 库房经理。管显存（KV Cache）够不够用。
    • table_manager: 座位经理。管这就餐记录表（Page Table），记录谁坐在哪。
    • decode_manager: 甜点部经理。管生成阶段（Decode），因为生成阶段也会占内存，得防着点。
    • pending_list: 排号单。手里拿个小本本，用来记排队的顾客。

2. 接待顾客 (接收请求)

  • 代码位置: add_raw_req
  • 任务: 门口来了个新顾客（UserMsg）。
  • 动作:
    1. 把顾客的 ID、想吃什么（input_ids）、预计吃多久（output_len）记在小本本（pending_list）的最后一行。
    2. 此时不安排座位，只是记下来。

3. 核心调度 (安排这一批谁能进)

这是最复杂的 schedule_next_batch 方法。领班每隔一小会儿就要做一次这个任务。

  • Task 3.1: 检查有没有人排队

    • 如果 pending_list 是空的，直接休息 (return None)。

  • Task 3.2: 盘点资源 (算算家底)

    • 看看座位表 (page_table) 还在吗。
    • 关键点: 问问甜点部（Decode）现在占了多少资源 (offset)。因为显存是共享的，必须把那边正在用的或者即将用的预留出来。

  • Task 3.3: 遍历排队的人 (FIFO 先来后到)

    • 开始从 pending_list 第一个人开始看。

  • Task 3.4: 决定能不能接待这个人 (资源硬性检查)

    • 检查: 计算预算 (prefill_budget)、库房剩余空间 (available_size)、座位表剩余行数。
    • 判断: 如果任何一个资源 <= 0，说明餐厅爆满或者厨师累趴了，停止接客 (break)。

  • Task 3.5: 查查老黄历 (缓存匹配 / Radix Attention)

    • 代码: handle, match_indices = self.cache_manager.match_req(req)
    • 解释: 这是高级功能。看看这个顾客点的菜（Prompt），是不是跟以前某个顾客点的一样？比如大家都用了同样的“系统提示词”。
    • 如果一样，直接复用以前算好的结果（match_indices），这就省力了。
    • cached_len: 已经做好的菜的数量。
    • extend_len: 需要厨师新做的菜的数量（总输入 - 已缓存）。

  • Task 3.6: 估算风险 (能不能塞得下)

    • 代码: estimated_len = extend_len + req.output_len
    • 解释: 估算这个顾客吃完饭（Input + Output）总共要占多少内存。
    • 判断 1: if extend_len > prefill_budget: 如果新做的菜太多，超过了这一批的计算预算，这批先不接了，下一批再说 (break)。
    • 判断 2: if estimated_len > ...: 如果库房剩下的空间不够他吃完全程，为了防止吃到一半没内存报错，现在就拒绝 (break)。

  • Task 3.7: 锁定资源 (Locking)

    • 代码: self.cache_manager.lock(handle)
    • 解释: 既然决定复用之前的缓存，先把那部分缓存锁住，别被别人清空了。
    • 再次检查: 锁住之后再检查一遍内存够不够（防止并发情况下的资源竞争）。如果不够，解锁并放弃。

  • Task 3.8: 正式分配 (Allocation)

    • 分配显存: cache_manager.allocate(extend_len)。给新做的菜分配空间。
    • 分配座位: table_manager.allocate()。给这个顾客开一个新的座位号（Page Table Index）。
    • 扣除预算: prefill_budget -= extend_len。厨师的精力减少了。

  • Task 3.9: 填表 (Update Page Table)

    • 把“复用的旧缓存位置”和“新分配的位置”都填到这个顾客的座位表里 (page_entry)。这样模型就知道去哪读取数据了。

  • Task 3.10: 打包任务 (Create Req)

    • 把所有准备好的信息（ID、输入、座位号、缓存句柄等）打包成一个 Req 对象，放到 result 列表里。

  • Task 3.11: 善后 (Cleanup)

    • 如果 result 里有人，把这些人从排队小本本 (pending_list) 里划掉。
    • 把 result 交给下一道工序（模型计算）。

总结文中的核心观点

  1. 先来后到 (FIFO): 严格按照排队顺序处理请求。
  2. 前缀缓存 (Prefix Caching / Radix Attention): 这是代码里 match_req 的部分。它极大地优化了性能，如果你的 Prompt 前半部分和以前一样，它就不重新算了，直接复用。
  3. 资源预留: 在接客之前，必须算清楚这个顾客未来（生成 Output 时）需要的总内存，如果内存不够，为了安全起见，现在就不让他开始运行。
  4. 计算预算控制: 也就是 prefill_budget。不能一次性把所有排队的人都放进去，否则计算量太大，显卡会卡死（Latency 变高）。每次只处理一定数量的 Token。
