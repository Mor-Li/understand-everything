python/minisgl/scheduler/scheduler.py

这份代码实现了一个 LLM 推理服务的调度器 (Scheduler)。

你可以把 Scheduler 想象成一个 “餐厅经理”。他的工作不是亲自做菜（做菜是 Engine 的工作），而是负责接单、安排谁先吃、谁后吃、把做好的菜端给客人，并管理餐厅的座位（显存）。

为了让你读懂，我把这个代码的逻辑拆解成一份 Task Todo List (任务清单)，按代码运行的生命周期一步步来讲。

Task 1: 开店准备 (初始化 __init__)

在一切开始之前，经理需要把店里的设施准备好。

  1. 启动引擎 (self.engine):
    • 经理得先把厨师团队（Engine）叫醒，准备好 GPU 资源。
  2. 建立通信渠道 (ZMQ Queues):
    • 对外: 建立“收信箱” (recv_tokenizer) 接收用户的 Prompt；建立“发信箱” (send_tokenizer) 把生成的 Token 发回给用户。
    • 对内 (多卡并行): 如果有多个 GPU (TP > 1)，Rank 0 (主卡) 负责接收外部消息，然后通过广播 (send_ranks) 告诉其他从卡；从卡 (rank1) 只需要监听主卡的指令。
  3. 招聘管理员 (Managers):
    • PageTableManager: 管理显存页表（类似于管理餐厅座位表）。
    • CacheManager: 管理 KV Cache（类似于管理餐盘和半成品）。
    • PrefillManager: 负责处理新来的客人（首字推理/Prefill 阶段）。
    • DecodeManager: 负责处理正在吃的客人（生成后续 Token/Decode 阶段）。

Task 2: 每日循环 (main_loop & run_forever)

这是代码的核心，经理开始无限循环地处理事务。我们将 main_loop 拆解为每一步的 Todo：

Step 2.1: 检查信箱 (_recv_msg_*)

  • 动作: 经理去门口看看有没有新订单。
  • 逻辑:
    • 如果当前 GPU 很忙（有任务在跑），就非阻塞地看一眼（有信就拿，没信就算）。
    • 如果当前 GPU 很闲（没任务），就阻塞等待（一直等到有信来为止，省电）。
  • 多卡处理:
    • 如果是主卡：从外界收信，然后转发给从卡。
    • 如果是从卡：只等主卡的转发。

Step 2.2: 处理新订单 (_process_one_msg)

  • 动作: 打开信封看内容。
  • 逻辑:
    • 如果是 UserMsg (用户请求): 把它扔进 prefill_manager 的等待队列里（相当于客人在门口排队拿号）。
    • 如果是 ExitMsg: 关门下班。

Step 2.3: 决定下一批做什么 (_schedule_next_batch)

  • 动作: 经理看一眼排队区（Prefill）和用餐区（Decode），决定下一秒让厨师做什么。
  • 逻辑:
    • 优先 Prefill: 如果有新客人排队，且显存够用，优先处理新客人的 Prompt（因为 Prefill 吞吐量大）。
    • 其次 Decode: 如果没有新客人，或者显存不够塞入新客人，就继续给正在生成的请求算下一个 Token。
    • 结果: 生成一个 Batch 对象，里面包含了这次要算的请求列表。

Step 2.4: 厨师开火 (engine.forward_batch)

  • 动作: 把决定好的 Batch 交给 Engine。
  • 逻辑:
    • engine.prepare_batch: 准备数据。
    • engine.forward_batch: GPU 开始计算。
    • 关键点: 这里使用了 CUDA Stream。GPU 在跑的时候，CPU 不会傻等，而是继续往下走（去处理上一批的结果），这叫“流水线并行”。

Step 2.5: 处理上一批的菜 (_reply_tokenizer_* & _filter_finished_reqs)

  • 动作: 这里的逻辑稍微有点绕。因为 GPU 是异步的，当 CPU 跑到这一步时，处理的其实是上一次循环提交给 GPU 的任务结果。
  • 逻辑:
    • 拿到上一次 GPU 算出来的 Token。
    • 检查是否结束: 这个请求是不是生成了结束符 (EOS) 或者达到了最大长度？
    • 如果结束了:
      • 回收显存 (table_manager.free, cache_manager.free)。
      • 从 decode_manager 里把这个请求踢出去。
    • 发货: 把生成的 Token 封装成消息，通过 ZMQ 发回给前端/用户。

总结：代码的生命周期图解

你可以把整个 scheduler.py 看作在维护这样一个死循环：

  1. 收信: 来了新请求？ -> 加入等待队列。
  2. 调度:
    • 显存够吗？
    • 先做新来的 (Prefill) 还是继续做旧的 (Decode)？
    • 选出一批任务 (Batch)。
  3. 执行 (GPU): 告诉 GPU 去跑这个 Batch (GPU 在后台跑，CPU 继续往下)。
  4. 善后 (CPU):
    • 看看上一个 Batch 跑完的结果。
    • 哪个请求跑完了？ -> 释放显存。
    • 把生成的字发给用户。
  5. 回到第 1 步。

  • 想看怎么选任务的: 看 _schedule_next_batch。
  • 想看怎么判断请求结束的: 看 _filter_finished_reqs。
  • 想看主循环逻辑的: 看 main_loop。
