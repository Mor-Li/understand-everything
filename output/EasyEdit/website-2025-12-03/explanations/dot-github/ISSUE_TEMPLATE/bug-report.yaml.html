.github/ISSUE_TEMPLATE/bug-report.yaml

别担心，这段代码其实并不是那种“用来运行的程序”，而是一张“在线问卷的设计图”。

具体来说，这是 GitHub 平台上用来给开发者提 Bug（报错）时填写的表单模板。

想象一下，你在这个软件（EasyEdit）的使用中遇到了问题，想要告诉开发者。开发者为了防止大家乱写（比如只写一句“软件坏了”），就用这个文件规定了：“你想报错，必须按顺序回答以下几个问题”。

我把你作为“报错者”，根据这个文件的要求，整理成了一份 Task Todo List（任务清单）。你只要按这个步骤走，就完全理解这个文件的意思了：

📋 任务清单：如何向 EasyEdit 团队提交一个合格的 Bug 报告

任务 0：准备工作

  • 文件对应含义：name: "🐛 Bug Report" 和 labels: [ "bug" ]
  • 你要做的：当你点击“新建 Issue”时，选择这个带有 🐛 图标的选项。系统会自动给你的报告打上 "bug" 的标签，方便分类。

任务 1：描述你遇到的问题 (必填)

  • 文件对应含义：
    • label: Describe the bug (描述 Bug)
    • required: true (这是必填项)
  • 你的 To-Do：
    • 用简洁清晰的语言写下：你到底遇到了什么错误？
    • 例子：“我在使用 MEND 方法编辑句子时，输出的结果没有任何变化，这不对。”

任务 2：证明并复现这个问题 (必填 & 最重要)

  • 文件对应含义：
    • label: To Reproduce (如何复现)
    • description: 这里面写了一大堆字，其实是开发者的“免责声明”和“要求”。
  • 你的 To-Do (分步执行)：
    1. 先查文档：开发者要求你在报错前，先去读一下 README.md 和 README_2.md，确认是不是你自己用错了，而不是软件的问题。
    2. 自报家门：写下你的电脑环境（比如：Python 是几点几版本？操作系统是 Windows 还是 Linux？依赖包的版本是多少？）。
    3. 提供代码：把能导致出错的那段代码或者命令贴出来。
      • 注意：要用代码块格式包裹起来（就是用 ``` 包裹）。
    4. 展示报错信息：程序崩溃时弹出的那些红色的英文乱码（Traceback），截图或者复制粘贴上来。

任务 3：描述你原本期待的结果 (必填)

  • 文件对应含义：label: Expected behavior (预期行为)
  • 你的 To-Do：
    • 告诉开发者：如果没有出错，你觉得程序应该输出什么？
    • 例子：“我原本期待输出的句子应该是被修改过的，而不是和原句一模一样。”

总结：这个文件到底在讲啥？

它的核心观点只有一个：

“为了让我们（开发者）能高效地修好 Bug，请你（用户）在报错时不要废话，直接提供：环境信息、复现步骤、报错日志和预期结果。”

这个 .yaml 文件就是强制把这几个问题变成一个个输入框，如果你不填完这些“必填项”，你就没法提交报告。
