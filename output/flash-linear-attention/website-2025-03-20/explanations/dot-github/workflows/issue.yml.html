.github/workflows/issue.yml

没问题。你可以把这个文件想象成你雇佣了一个不知疲倦的机器人管理员，你给他列了一张“每周清洁任务清单” (ToDo List)，让他专门负责清理项目中那些没人理会的旧帖子（Issues）。

这个文件的核心目的就是：自动关闭长期不活跃的 Issues，防止项目堆积太多垃圾信息。

下面我按照这个机器人干活的顺序，把你给他的任务清单一步步列出来：

🤖 机器人管理员的任务清单 (ToDo List)

1. 设定闹钟：什么时候开始干活？

  • 代码对应： cron: "0 0 * * 0"
  • 任务说明： “每周日凌晨 0 点（UTC时间），准时醒来开始工作。”
  • 解读： 这个脚本不是一直运行的，而是每周运行一次，频率不高，为了节省资源。

2. 第一轮筛选：寻找“僵尸”帖子

  • 代码对应： days-before-issue-stale: 30
  • 任务说明： “去检查所有的 Issue，如果发现哪个 Issue 已经连续 30天 没有任何人回复、修改或操作，就把它标记为‘快过期了’。”
  • 解读： 这是一个筛选机制，定义了什么是“旧”帖子。

3. 贴标签 & 发警告：给用户发通知

  • 代码对应：
    • stale-issue-label: "stale"
    • stale-issue-message: "This issue is stale..."
  • 任务说明： “对于上面找到的那些 30 天没动静的帖子，给它贴上一个叫 stale (陈旧) 的标签，并且在底下自动回复一句话：‘这个帖子 30 天没动静了，看来是没人管了。’”
  • 解读： 这是给提问者一个提醒（Poke），告诉他“如果你还关心这个问题，赶紧回复一下，否则我要关贴了”。

4. 设立 VIP 保护名单：别动这些帖子

  • 代码对应： exempt-issue-labels: "enhancement"
  • 任务说明： “但是在清理的时候注意！如果这个帖子被打上了 enhancement (功能增强/建议) 的标签，千万不要把它标记为过期，哪怕它一万年没人理也别动它。”
  • 解读： 有些长期的功能建议（Feature Request）可能很久才会被开发，不能因为没人聊天就把它关了。

5. 第二轮筛选：处决“死”帖子

  • 代码对应： days-before-issue-close: 7
  • 任务说明： “去检查那些已经被贴上 stale 标签的帖子。如果贴了标签之后又过了 7天，还是没有任何人说话（仍然处于静默状态），那就准备动手了。”
  • 解读： 这是给用户的“宽限期”。从警告到真正关闭，有 7 天的时间让你去“救”这个帖子。

6. 执行关闭：彻底关贴

  • 代码对应： close-issue-message: "This issue was closed..."
  • 任务说明： “对于那些过了宽限期还没人理的帖子，直接点击 Close (关闭) 按钮，并留下一句话：‘因为贴了过期标签 7 天后还是没人理，所以我把它关了。’”
  • 解读： 只有在这个时候，Issue 才会被真正关闭。

7. 忽略代码合并请求 (Pull Requests)

  • 代码对应：
    • days-before-pr-stale: -1
    • days-before-pr-close: -1
  • 任务说明： “对了，这个清理规则只针对 Issue (讨论帖)。对于 Pull Requests (代码贡献)，不管放了多久，你都别管，别标记过期也别关闭。”
  • 解读： -1 在这里代表“禁用/关闭功能”。因为代码贡献通常比讨论帖更重要，不能随便自动关闭。

总结一下这个机器人的逻辑：

  1. 周日上班。
  2. 30天没动静？ -> 贴条警告：“我要关了哦！”
  3. 又过了7天还没动静？ -> 直接关闭：“拜拜！”
  4. 如果是“功能建议”或者“代码贡献”？ -> 假装没看见，永远不关。

这在开源项目中非常常见，用来防止 Issue 列表里堆积成百上千个几年前的、没人维护的过时问题。
