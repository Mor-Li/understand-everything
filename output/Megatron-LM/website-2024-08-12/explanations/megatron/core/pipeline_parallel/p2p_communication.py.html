megatron/core/pipeline_parallel/p2p_communication.py

这份代码是 Megatron-LM 中用于 流水线并行 (Pipeline Parallelism) 的核心通信模块。

简单来说，当一个巨大的模型（比如 GPT-3）因为太大而塞不进一张显卡时，我们会把它像切香肠一样切成几段，每一段放在不同的显卡（GPU）上。 * GPU 0 计算第 1-10 层 * GPU 1 计算第 11-20 层 * ...

这个文件的作用就是： 让 GPU 0 把算好的结果（激活值）扔给 GPU 1，同时让 GPU 1 把算好的梯度（反向传播时）扔回给 GPU 0。这就叫 P2P (Point-to-Point) 通信。

为了让你看懂，我把它想象成一个 “流水线搬运工的操作手册”，并列一个 Task List (待办事项)。

📋 Task Todo List：流水线搬运工的一天

想象你是一个流水线上的工人（某个 GPU Rank），你的任务是处理数据并传递给上下游。这个文件就是执行以下流程：

  1. Task 1: 确认交接暗号 (Shape Communication)

    • 问题：有时候包裹（Tensor）的大小是不固定的（比如句子长度变了）。
    • 动作：在传正式数据前，先发一个小纸条，告诉对方：“嘿，待会儿我要发给你的数据形状是 [2048, 4, 4096]”。
    • 对应代码：_communicate_shapes

  2. Task 2: 准备空箱子 (Memory Allocation)

    • 问题：你要接收隔壁传来的数据，得先在显存里划出一块空地来接。
    • 动作：根据 Task 1 拿到的形状，创建一个空的 Tensor (torch.empty)，准备接货。
    • 对应代码：_communicate 函数中间的 if recv_prev: ... torch.empty(...)

  3. Task 3: 制定交通规则 (Traffic Control / P2P Ops)

    • 问题：如果我和隔壁同时往对方脸上扔包裹，路会堵死（死锁，Deadlock）。
    • 动作：
      • 方案 A (普通模式)：偶数号工人先发，奇数号工人先收；然后再反过来。
      • 方案 B (批量模式)：使用 PyTorch 的高级功能 batch_isend_irecv，让底层去优化并发。
    • 对应代码：_p2p_ops (手动调度) 和 _batched_p2p_ops (自动调度)。

  4. Task 4: 执行发送与接收 (Execute Communication)

    • 动作：实际调用 isend (异步发送) 和 irecv (异步接收)。
    • 对应代码：_communicate 是总指挥，它调用上面的函数。

  5. Task 5: 封装成傻瓜式按钮 (Public API)

    • 动作：提供简单好用的按钮给外部训练代码调用，比如“向前传”、“向后传”、“一边接前一边发后”。
    • 对应代码：recv_forward, send_backward, send_forward_recv_backward 等。

🔍 逐步代码解析 (Step-by-Step)

现在我们按照上面的 Task List，一步步看代码在干啥。

第一步：解决变长数据问题 (_communicate_shapes)

如果你的模型处理的句子长度是固定的，这一步会跳过。但如果长度可变： * 代码逻辑： * 创建小张量 torch.empty((3)) (用来存长、宽、高)。 * 把自己的 Tensor 尺寸填进去。 * 发给邻居 (Prev 或 Next)，并接收邻居发来的尺寸。 * 返回 recv_prev_shape，这样主程序就知道该分配多大的显存了。

第二步：核心调度员 (_communicate)

这是这个文件里最重要的私有函数（Helper Method）。其他的 send_forward 之类都只是它的“马甲”。 * 输入参数： * tensor_send_next: 要发给下游的数据（Forward pass 的输出）。 * tensor_send_prev: 要发给上游的数据（Backward pass 的梯度）。 * recv_prev: 是否要从上游接数据？ * recv_next: 是否要从下游接数据？ * 流程： 1. 定形状：如果需要，调用 _communicate_shapes。 2. 挖坑（分配内存）：tensor_recv_prev = torch.empty(...)。如果不先挖坑，数据来了没地儿放。 3. 选快递公司： * 如果是 use_ring_exchange_p2p：用环形交换。 * 如果是 batch_p2p_comm：用批量 P2P（_batched_p2p_ops）。 * 否则：用手动 P2P（_p2p_ops）。 4. 等待完成：req.wait()，确保数据发完/收完再进行下一步计算。

第三步：避免死锁的交通规则 (_p2p_ops)

这段代码看起来很多 if-else，其实是为了防止死锁。 * 死锁场景：Rank 0 想发给 Rank 1，Rank 1 也想发给 Rank 0。两人都占着发送通道等待对方接收，结果谁也动不了。 * 解决方案 (代码中的逻辑)： * if rank % 2 == 0: 偶数 Rank (0, 2, 4...) 先发后收。 * else: 奇数 Rank (1, 3, 5...) 先收后发。 * 这样就形成了一个完美的闭环，不会堵车。

第四步：对外提供的“傻瓜按钮” (Public APIs)

这是外部程序（如 megatron/schedules.py）真正调用的函数。它们只是对 _communicate 的简单封装。

  1. recv_forward:

    • 场景：我是 Rank 1，我要开始正向计算了，我得先拿到 Rank 0 算好的结果。
    • 操作：只收上游 (recv_prev=True)，不发。

  2. send_forward:

    • 场景：我是 Rank 0，我算完了，把结果扔给 Rank 1。
    • 操作：只发下游 (tensor_send_next=output)，不收。

  3. recv_backward:

    • 场景：反向传播时，我是 Rank 0，我得等 Rank 1 把梯度传回来。
    • 操作：只收下游 (recv_next=True)。

  4. send_forward_recv_backward (组合拳):

    • 场景：这是流水线并行最复杂的时刻（1F1B 策略）。
    • 含义：我刚算完正向传播（Forward），要把结果给下游；同时，下游刚算完反向传播（Backward），要把梯度给我。
    • 操作：既发下游，又收下游。这俩动作合并在一起做，效率最高。

  5. send_forward_recv_forward:

    • 场景：通常用于数据并行和流水线并行混合时，或者特定的调度策略（Interleaved Schedule）。
    • 操作：把我的结果发给下游，同时接收上游发给我的新数据。

总结

这个文件其实就在干一件事：在流水线并行的不同 GPU 之间，安全、高效地搬运 Tensor（数据和梯度）。

  • 它处理了“先发还是先收”的顺序问题（防死锁）。
  • 它处理了“不知道对方发多大包”的问题（传 Shape）。
  • 它提供了“各种组合的收发接口”给训练主循环使用。
