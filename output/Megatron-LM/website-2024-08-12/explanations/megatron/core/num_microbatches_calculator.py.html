megatron/core/num_microbatches_calculator.py

没问题，这个文件看起来全是代码和数学逻辑，确实容易让人头大。

简单来说，这个文件的核心作用就是做一道除法题。

背景知识： 在训练大模型时，我们想让模型一次看很多数据（比如 1000 条，这叫 Global Batch Size），这样训练才稳。但是，显卡显存有限，一次塞不进 1000 条，只能塞 10 条（这叫 Micro Batch Size）。 如果你有 8 张卡（Data Parallel Size），那么一次并行只能处理 $10 \times 8 = 80$ 条。 为了凑够 1000 条，显卡得跑多少轮（Num Micro Batches）才能更新一次参数？ 答案是：$1000 \div 80 = 12.5$ (取整即 12 或 13 轮)。

这个文件就是负责算出这个“12”，并且处理Global Batch Size 会变大（Rampup）的情况。

任务清单 (Task List)

为了帮你理解，我把这个代码执行的逻辑拆解成一个 Task Todo List，这是代码在运行时一步步做的事情：

  1. [准备] 定义三个核心数字：
    • 我要凑够多少数据？(global_batch_size)
    • 一张卡一次能吃多少？(micro_batch_size)
    • 我有多少张卡在并行干活？(data_parallel_size)
  2. [决策] 选定一种计算策略：
    • 策略 A (Constant): 从头到尾 Global Batch Size 都不变。
    • 策略 B (Rampup): 刚开始训练怕不稳定，Global Batch Size 从小一点开始，慢慢变大，直到设定值。
  3. [初始化] 创建计算器：
    • 根据策略 A 或 B，生成一个全局唯一的计算器对象（存放在 _GLOBAL_NUM_MICROBATCHES_CALCULATOR）。
  4. [循环] 训练过程中的每一步：
    • Task 4.1: 告诉计算器：“我已经训练了多少样本了（consumed_samples）？”
    • Task 4.2 (如果是策略 B): 计算器判断：“根据进度，现在的 Global Batch Size 该变大了吗？” -> 更新当前的 Global Batch Size。
    • Task 4.3: 做除法：当前 Global Batch Size / (Micro Batch * 卡数) = 我们需要跑几轮 Micro Batches。
  5. [输出] 获取结果：
    • Megatron 的其他代码调用 get_num_microbatches() 拿到这个数字，去安排显卡干活。

逐步详解 (Step-by-Step)

现在我们对应代码，把上面的 List 展开讲讲。

第一步：核心数学公式

代码里反复出现一个逻辑，体现在 ConstantNumMicroBatchesCalculator 类中：

micro_batch_times_data_parallel = micro_batch_size * data_parallel_size
self.num_micro_batches = global_batch_size // micro_batch_times_data_parallel
  • 翻译：
    • micro_batch_times_data_parallel = 所有显卡加起来，跑一轮能处理多少数据。
    • num_micro_batches = 总目标除以单轮能力，也就是梯度累积的步数 (Gradient Accumulation Steps)。
  • 检查：代码里有很多 assert，是用来确保能整除。如果不能整除，数据对不齐，程序会报错。

第二步：策略 A - 固定模式 (Constant)

这是最简单的模式。 * 代码对应：ConstantNumMicroBatchesCalculator 类。 * 逻辑： * 初始化时算好 num_micro_batches 是多少。 * 不管训练到第几步，这个数字永远不变。 * update() 函数是空的（pass），因为它不需要更新。

第三步：策略 B - 爬坡模式 (Rampup)

这是最复杂的模式，也是让你看不懂的地方。 * 代码对应：RampupBatchsizeNumMicroBatchesCalculator 类。 * 为什么要爬坡？ 模型刚开始学东西时很脆弱，如果一次塞太多数据（大 Global Batch），容易学崩。所以要从小的 Global Batch 开始，慢慢加到大的。 * 参数意思： * start_global_batch_size: 起步价（比如从 128 开始）。 * batch_size_increment: 每次加多少（比如每次加 64）。 * ramup_samples: 用多少样本的时间完成爬坡（比如前 100万个样本里慢慢加）。 * Update 逻辑 (核心难点)： 每次调用 update(consumed_samples)： 1. 如果 consumed_samples 超过了 ramup_samples（爬坡期过了），那就用最终的 global_batch_size。 2. 如果还在爬坡期： * 算出当前处于第几个台阶 (steps)。 * 当前 GBS = 起步价 + (台阶数 * 每次加价)。 3. 重新做除法：用新的当前 GBS 算出新的 num_micro_batches。

第四步：全局单例模式 (Global Variable)

你会看到很多 global _GLOBAL_NUM_MICROBATCHES_CALCULATOR。 * 逻辑： * Megatron 框架很大，很多地方都需要知道“我现在该跑几个 micro batch”。 * 为了不把这个计算器对象传得到处都是，它搞了一个全局变量。 * init_num_microbatches_calculator：程序启动时调用一次，把计算器造好放进去。 * get_num_microbatches()：任何地方调用这个函数，实际上就是问那个全局变量要数字。

总结文中的观点

这个文件不讲大道理，它就是一个管家。

  1. 职责：根据当前的训练进度，告诉系统每一轮参数更新需要切分多少个小批次（Micro Batches）。
  2. 观点/假设：
    • Global Batch Size 必须能被 (Micro Batch Size * Data Parallel Size) 整除。
    • 如果使用了 Rampup（爬坡），Global Batch Size 会随时间线性增长，导致 Micro Batches 的数量也会动态变化。

一句人话总结： 这个文件就是一个计算器，用来算出为了凑够一大批数据（Global Batch），每张显卡需要分几小口（Micro Batch）吃完。如果处于训练初期（Rampup），这个“一大批”的数量会变，所以它得实时重新算。
