megatron/core/tensor_parallel/data.py

这份代码主要解决的是大模型训练（Megatron-LM）中“张量并行（Tensor Parallel）”场景下的数据同步问题。

简单来说，当多个 GPU 一起合作算一个大矩阵时，通常只有“组长”（Rank 0）手里拿着原始数据（比如输入的一句话），“组员”（其他 Rank）手里是空的。

这个文件的任务就是：组长把手里的数据“复印”一份，分发给所有组员，并且要保证格式完全一样。

为了让你彻底看懂，我把这个过程拆解成一个 5步走的 Todo List。

核心任务 Todo List

  1. 【准备工作】同步“说明书”（元数据）： 组员不知道数据长什么样（几行几列？），组长得先发个说明书过去。
  2. 【组长操作】数据打包（Flatten）： 组长手里有很多零散的小数据，为了发快递方便，把它们拼成一条长长的数据链。
  3. 【组员操作】准备容器： 组员根据“说明书”，在自己的显存里挖好坑，准备接数据。
  4. 【核心动作】广播（Broadcast）： 组长一声令下，把那条长长的数据链瞬间复制到所有组员的显存里。
  5. 【收尾工作】解包还原（Unpack）： 所有人把这条长数据链，按照“说明书”切开，还原成最初的字典格式。

详细步骤讲解

下面我按照这个 List，结合代码给你一步步讲：

1. 【准备工作】同步“说明书”（元数据）

对应函数： _build_key_size_numel_dictionaries

在网络传输中，接收方必须知道对方要发多大的东西过来。 * 组长（Rank 0）：读取数据的形状（比如 [4, 1024]）。 * 组员：此时是一脸懵逼的。

代码逻辑： * 填表：代码里定义了一个 sizes 数组。组长把每个数据的维度（长、宽、高）填进去。 * 发送表：torch.distributed.broadcast(sizes_cuda, ...)。组长把这张记录了尺寸的“表”发给所有人。 * 计算：组员收到表后，算出：“哦，一共要发 1000 个数字过来，第一个数据是 2x5，第二个是...”

代码片段： ```python

组长把尺寸填进 sizes 列表

2. 【组长操作】数据打包（Flatten）

对应函数： broadcast_data 中的 if rank == 0 部分

网络传输最怕“碎”。发 100 个 1KB 的包，不如发 1 个 100KB 的包快。所以我们要把字典里的数据（Key-Value）全部“压扁”。

代码逻辑： * 检查类型：_check_data_types 确保大家都是 float32 或者 float16，不能混着来。 * 压扁：使用 view(-1) 把二维、三维矩阵拉成一条直线。 * 拼接：使用 torch.cat 把所有拉直的数据拼在一起，变成一个超级长的 1D Tensor（flatten_data）。

代码片段： python if get_tensor_model_parallel_rank() == 0: # 把字典里所有 value 拉直，拼成一条长龙 flatten_data = torch.cat([data[key].contiguous().view(-1) for key in keys], dim=0).cuda()

3. 【组员操作】准备容器

对应函数： broadcast_data 中的 else 部分

组员现在手里有了第1步发来的“说明书”，知道总共要接收多少个数字（total_numel）。

代码逻辑： * 组员申请一块显存，大小等于 total_numel，就像准备好一个空箱子。

代码片段： python else: # 组员创建一个空的 Tensor，准备接球 flatten_data = torch.empty(total_numel, device=..., dtype=datatype)

4. 【核心动作】广播（Broadcast）

对应函数： broadcast_data 中的 broadcast 调用

这是最关键的一步。利用 NCCL 通信库，把数据从 Rank 0 复制到 Group 内的所有人。

代码逻辑： * src_rank 是发送者（组长）。 * group 是通信组（张量并行的所有 GPU）。 * 执行完这行代码后，所有组员那个空的 flatten_data 里瞬间填满了和组长一模一样的数据。

代码片段： python torch.distributed.broadcast( flatten_data, get_tensor_model_parallel_src_rank(), # 发送者是谁 group=get_tensor_model_parallel_group() # 发给谁 )

对应函数： broadcast_data 的最后部分

现在大家手里都有一条一模一样的“长龙”数据，但程序后续需要的是字典（Dictionary），不是长龙。

总结

这个文件的核心逻辑就是： 测量尺寸 -> 广播尺寸 -> 压扁数据 -> 广播数据 -> 还原数据。

为什么要这么麻烦？ 因为在深度学习框架（PyTorch）的分布式通信中，接收方必须预先知道要接收的数据 Tensor 的形状才能分配显存。而这个脚本巧妙地先传“形状”，再传“内容”，从而实现了任意复杂字典数据的自动同步。
