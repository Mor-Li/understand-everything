megatron/core/tensor_parallel/random.py

这份代码确实比较晦涩，因为它处理的是分布式大模型训练中最让人头疼的问题之一：随机性管理（Randomness Management）。

简单来说，在训练像 GPT 这样的大模型时，我们有几百张显卡。有些时候我们需要所有显卡生成一样的随机数（比如初始化参数），有些时候我们需要它们生成不一样的随机数（比如做 Tensor Parallel 切分时的 Dropout）。

为了让你读懂这份代码，我为你列了一个 “学习任务清单 (Todo List)”。按照这个顺序，我们一步步拆解文中的观点和代码逻辑。

📋 学习任务清单 (Todo List)

  1. Task 0: 理解核心痛点（为什么原生 PyTorch 不够用？）
  2. Task 1: 打造基础工具（如何高效设置随机种子？）
  3. Task 2: 构建“多重人格”管理器（RNG Tracker 是什么？）
  4. Task 3: 分配身份（如何为不同的并行模式分配种子？）
  5. Task 4: 实战应用——“时光倒流”（Checkpointing 中的随机状态恢复）

🟢 Task 0: 理解核心痛点

观点： 在分布式训练中，显卡不仅要知道“我是谁”，还要能在不同的场景下切换“随机数生成模式”。

  • 场景 A（数据并行）： 假设你有两组显卡训练同一个模型。为了保证训练一致性，非并行部分的 Dropout 可能需要随机数是一样的。
  • 场景 B（模型并行）： 一个大的矩阵被切分到了两张卡上。如果这两张卡在做 Dropout 时生成的随机掩码（mask）一模一样，那就相当于没切分，数学上就错了。所以这里它们必须生成不同的随机数。

结论： 我们不能只用一个全局的 torch.manual_seed，我们需要一个能随时切换随机数状态的工具。

🟢 Task 1: 打造基础工具

代码对应： _set_cuda_rng_state(new_state, device=-1)

这一步很简单，就是造一个轮子。 * 功能： 强行把当前显卡的随机数生成器（RNG）的状态设置成指定的值。 * 细节： 代码里写了一堆 if hasattr... else...，这纯粹是为了兼容不同版本的 PyTorch（旧版和新版 API 不一样）。 * 重点： 注意注释里提到的 cloning 问题。直接设置状态比复制状态要快，这是为了性能优化。

🟢 Task 2: 构建“多重人格”管理器

代码对应： class CudaRNGStatesTracker

这是文件的核心类。你可以把它想象成一个“存档管理器”。

  • 它的工作原理：
    • 它内部有一个字典 self.states_，用来保存不同名字的随机状态。
    • 比如：{'model-parallel': 状态A, 'data-parallel': 状态B}。
  • 关键方法 add(name, seed)：
    • 给我一个种子，我生成一个状态，存进字典里，标记为 name。
  • 关键方法 fork(name)： (最重要！)
    • 这是一个上下文管理器（with 语句）。
    • 流程：
      1. 先保存当前显卡正在用的随机状态（存档）。
      2. 读取你指定的 name 对应的随机状态（读档，比如读取 'model-parallel' 的状态）。
      3. 加载这个状态，让你运行接下来的代码（比如做一次 Dropout）。
      4. 运行完后，把刚才的状态更新回字典（存盘）。
      5. 最后，恢复最开始保存的状态（回档）。
    • 比喻： 就像你打游戏，进副本前先存个档，切到“副本模式”打怪，打完出来，切回“大地图模式”。

🟢 Task 3: 分配身份（初始化）

代码对应： model_parallel_cuda_manual_seed(seed)

现在工具有了，我们需要在训练开始时给每张卡分配种子。

  • 逻辑拆解：
    1. 数据并行种子 (data_parallel_seed)： 直接等于传入的 seed。这意味着，属于同一个模型并行组的卡，或者不同数据并行组的卡，只要初始 seed 一样，这部分就一样。
    2. 模型并行种子 (tensor_model_parallel_seed)： seed + rank。
      • 注意那个 get_tensor_model_parallel_rank()。这意味着，即便在同一台机器上，负责模型不同切片的显卡，拿到的种子是不一样的（因为 rank 不同）。
  • 操作流程：
    • 初始化 Tracker。
    • 把 data_parallel_seed 存入 Tracker，起名为 'data-parallel-rng'。
    • 把 tensor_model_parallel_seed 存入 Tracker，起名为 'model-parallel-rng'。

总结： 跑完这个函数后，每张显卡都记住了两套（或三套）随机数生成逻辑，随时准备切换。

🟢 Task 4: 实战应用——“时光倒流”

代码对应： class CheckpointFunction (以及 checkpoint 函数)

这是 Megatron 节省显存的大杀器——激活重算 (Activation Checkpointing)。

  • 背景： 为了省显存，我们在前向传播（Forward）时不保存中间结果，等到反向传播（Backward）时再重新算一遍 Forward。
  • 问题： 如果 Forward 里有 Dropout，第一次算和第二次重算时，如果随机数不一样，Dropout 丢掉的神经元就不一样，那算出来的梯度就是错的！
  • 解决方案（代码逻辑）：
    1. Forward 阶段：
      • 记录当前的 CPU 和 CUDA 随机状态 (ctx.fwd_cuda_rng_state)。
      • 记录 Tracker 里所有的状态 (ctx.fwd_cuda_rng_state_tracker)。
      • 正常计算，不保存中间激活值（省内存）。
    2. Backward 阶段（重算）：
      • 时光倒流： 把当前的随机状态强行设置回 Forward 阶段记录的那个状态 (_set_cuda_rng_state(ctx.fwd_cuda_rng_state))。
      • 恢复管理器： 把 Tracker 的状态也恢复回去。
      • 重跑 Forward： 此时因为随机种子完全复原，Dropout 的行为将和第一次一模一样。
      • 算出梯度。
      • 还原： 算完后，再把随机状态恢复成 Backward 开始时的样子，不影响后面的计算。

总结：这篇文章到底讲了啥？

这个文件其实就是为了解决一个问题：在显卡很乱、并行模式很复杂的环境下，如何精准控制每一次 Dropout 到底是用“全局统一”的随机数，还是“特立独行”的随机数，并且保证在“为了省显存而重算”的时候，能完美复现之前的随机行为。
