megatron/core/transformer/moe/token_dispatcher.py

这份代码确实比较硬核，因为它涉及到大模型分布式训练中最复杂的混合专家模型（MoE）的数据通信部分。

为了让你看懂，我们可以把这个文件想象成一个“物流分拣中心”的操作手册。

核心任务：MoE模型里有很多“专家”（Experts，也就是很多个小神经网络）。每个Token（数据包裹）需要被送到指定的“专家”那里去处理，处理完后再送回原来的位置。

这个文件就是负责“把Token送到对的GPU上”（Permutation/分发）以及“处理完把结果拿回来”（Unpermutation/还原）。

下面是一个由浅入深的 Task Todo List，带你一步步拆解：

✅ Task 1: 理解基类 (MoETokenDispatcher) —— 定义接口

目标：搞清楚这个系统只干两件事：“送出去”和“接回来”。

代码中的 class MoETokenDispatcher 是一个抽象基类（类似大纲），它规定了所有分发器必须实现的两个方法：

  1. token_permutation (分发/排列):
    • 输入: 原始Token，以及每个Token想去哪个专家的索引 (indices)。
    • 工作: 把Token重新以此排序，甚至发送到别的GPU上，让同一个专家的Token聚在一起。
  2. token_unpermutation (还原/归位):
    • 输入: 专家处理完的结果 (expert_output)。
    • 工作: 把这些打乱顺序的结果，按原来的顺序排回去，送回原来的GPU。

✅ Task 2: 理解第一种实现 (MoEAllGatherTokenDispatcher) —— “全收集”模式

目标：理解基于 AllGather 的分发逻辑。这通常用于专家并行度较低或者特定架构配置下。

核心逻辑：与其精准投递，不如把自己需要的东西从大家那里都抓取（Gather）过来。

  • Step 2.1: 初始化 (__init__)

    • 它记录了本地有哪些专家 (local_expert_indices)。
    • 它准备了一些掩码 (mask)，用来标记哪些Token是属于我本地专家的。

  • Step 2.2: 分发 (token_permutation)

    • 动作 1 (跨设备通信): 调用 gather。虽然名字叫分发，但它实际上是从其他GPU那里收集所有Token的信息。
    • 动作 2 (筛选): 收集来了一大堆Token，但我只保留分配给我本地专家的那些 (masked_select)。
    • 动作 3 (本地排序): 把留下的Token按专家ID排序 (argsort)，这样本地专家1的Token在一起，专家2的在一起，方便计算。
    • 结果: 此时，GPU上只有属于本地专家的Token，且排好序了。

  • Step 2.3: 还原 (token_unpermutation)

    • 动作: 专家算完了。现在要把结果还给原来的拥有者。
    • 通信: 使用 reduce_scatter。这是一个逆向过程，把计算结果“撒”回给原来的GPU。

✅ Task 3: 理解第二种实现 (MoEAlltoAllTokenDispatcher) —— “全交换”模式 (重难点)

目标：这是大规模MoE最常用的方式。效率更高，但逻辑更绕。

核心逻辑：点对点精准互换。我有给你的包裹，你有给我的包裹，我们同时交换（All-to-All）。

  • Step 3.1: 预处理 (preprocess)

    • 统计: 先数一数（bincount），我有多少Token要给GPU 1，多少给GPU 2...
    • 切分点 (splits): 计算好数据的切割点，告诉通信函数：“前100个发给Rank 0，接下来的50个发给Rank 1...”。

  • Step 3.2: 分发 (token_permutation)

    • 本地重排: 先在自己家里把Token整理好，按目的地（目标专家所在的GPU）归类。
    • 第一次通信 (TP AlltoAll): 如果开了张量并行（Tensor Parallel），先处理TP维度的数据交换。
    • 第二次通信 (EP AlltoAll): 这是关键。调用 tensor_parallel.all_to_all。
      • 意思就是：所有GPU同时互发数据。我把你需要的Token发给你，你把我的发给我。
    • 再次重排: 收到数据后，虽然都在我这了，但可能顺序是乱的（比如来自GPU1的数据在前，GPU2在后）。我需要再排一次序，让属于“本地专家A”的数据紧挨着，属于“本地专家B”的紧挨着。

  • Step 3.3: 还原 (token_unpermutation)

    • 完全逆向操作:
      1. 先本地逆向重排。
      2. 执行 All-to-All 通信（把处理完的数据发回原主）。
      3. 收到数据后，再根据最开始记录的索引，把Token还原回句子原本的顺序（比如“我爱吃苹果”，不能变成“爱我果苹吃”）。

✅ Task 4: 总结与对比 (Cheat Sheet)

为了帮你理清思路，对比一下这两个类：

特性 AllGather Dispatcher AlltoAll Dispatcher
比喻 自助餐模式：大家把菜都端出来，我只拿我盘子里想吃的（属于我本地专家的）。 快递模式：每个人打包好要寄给别人的包裹，统一交换，精准投递。
通信量 可能会有冗余传输（如果大部分Token都不属于我，我也可能得先看一眼）。 高效，只传输必要的数据。
适用场景 这里的实现通常结合了序列并行(SP)，用于处理特定的拓扑结构。 主流选择。大规模MoE训练的标准做法。
代码复杂度 较低，主要是筛选（Masking）。 较高，需要计算Splits，处理Padding（填充）和Capacity（容量限制）。

💡 重点代码段落翻译

如果你看到 MoEAlltoAllTokenDispatcher 里的这段：

# Permutation 1: input to AlltoAll input
permutated_local_input_tokens, self.reversed_local_input_permutation_mapping = permute(
    hidden_states,
    indices,
    ...
)

# Perform expert parallel AlltoAll communication
global_input_tokens = tensor_parallel.all_to_all(
    parallel_state.get_expert_model_parallel_group(),
    permutated_local_input_tokens,
    self.output_splits,
    self.input_splits,
)

人话翻译： 1. permute: 在本地先把包裹按目的地分好堆。 2. all_to_all: 叫快递员来，把分好堆的包裹一次性发给其他所有GPU，同时接收其他GPU发给我的包裹。

总结：这个文件就是MoE模型的交通指挥系统。没有它，Token就不知道该去哪个GPU找哪个专家，算完也回不来。
