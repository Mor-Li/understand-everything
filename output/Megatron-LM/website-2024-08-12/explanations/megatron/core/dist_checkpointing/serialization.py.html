megatron/core/dist_checkpointing/serialization.py

这份代码文件 serialization.py 是 Megatron-Core 中处理 分布式模型保存与加载（Checkpointing） 的核心入口文件。

简单来说，它的作用就是把 PyTorch 原生的 torch.save 和 torch.load 变成了 “分布式版”，专门用来处理那些大到无法放进单个 GPU 的超大模型。

为了让你看懂，我列了一个 学习任务清单 (To-Do List)，我们一步步来拆解这个文件。

📋 任务清单：一步步读懂分布式存档

✅ Task 1: 理解核心背景 (Why?)

目标：明白为什么要写这个文件，而不是直接用 torch.save。

  • 普通情况：你有一个小模型，直接 torch.save(model.state_dict(), "model.pt")，生成一个文件。
  • Megatron 的情况：模型有几千亿参数，被切分（Sharded）到了几百个 GPU 上。
    • 如果只存一个文件：内存会爆，写文件会慢死。
    • 解决办法：每个 GPU 只存自己那一部分数据，同时还需要存一些公共的配置信息。
  • 这个文件的角色：它是总指挥。它告诉各个 GPU：“准备好你们的数据，按照某种策略（Strategy），把数据存进文件夹里。”

✅ Task 2: 掌握核心词汇 (Vocabulary)

目标：看懂代码里的变量名都在指代什么。

  1. ShardedStateDict (切分状态字典):
    • 普通的 state_dict 里面全是真实的 Tensor 数据。
    • 这里的 ShardedStateDict 里面存的是 “数据的描述”（比如：这个 Tensor 叫什么，它是怎么被切分的，属于哪个 GPU）。
  2. ShardedTensor / ShardedObject:
    • 被切分的数据对象。
  3. Common vs Sharded:
    • Common (公共数据)：所有 GPU 都一样的小数据（比如迭代步数、学习率参数）。通常由 Rank 0 (主进程) 负责存。
    • Sharded (切分数据)：巨大的模型权重，每个 GPU 都不一样。
  4. Strategy (策略):
    • 保存的方法。比如是存成 PyTorch 格式，还是存成 Zarr 格式？是同步存还是异步存？

✅ Task 3: 解析 save 函数 (怎么存？)

目标：看懂 def save(...) 函数的流程。

想象这是一次 “集体搬家” 活动：

  1. 检查环境：
    • 代码：if torch.distributed.get_rank() == 0: ...
    • 解释：主进程检查目标文件夹是否存在，是不是空的。
  2. 分类整理：
    • 代码：extract_nonpersistent, extract_sharded_base
    • 解释：把东西分成三类：
      • 不保存的 (Non-persistent)：扔掉。
      • 公共的 (Common)：交给主进程打包。
      • 切分的 (Sharded)：这是大件家具，需要拆开。
  3. 保存公共部分：
    • 代码：common_strategy.save_common(...)
    • 解释：主进程把小件行李存成一个 common.pt。
  4. 保存切分部分：
    • 代码：sharded_strategy.save(...)
    • 解释：所有 GPU 同时开工，把自己显存里的那块模型权重写到硬盘上。
  5. 写元数据 (Metadata)：
    • 代码：save_config(...)
    • 解释：最后写一个说明书（metadata.json），记录这次搬家用了什么格式，方便以后读取。
  6. 异步保存 (Async) (可选)：
    • 代码：async_sharded_save
    • 解释：如果开启，GPU 把数据丢给 CPU 或后台线程去写硬盘，自己立刻回去继续训练，不耽误时间。

✅ Task 4: 解析 load 函数 (怎么读？)

目标：看懂 def load(...) 函数的流程。

加载比保存更难，因为你需要把硬盘上的碎片拼回显存里，还得对齐形状。

  1. 读取公共部分：
    • 代码：common_strategy.load_common(...)
    • 解释：先读那个 common.pt，获取基础信息。
  2. 准备“模具”：
    • 代码：sharded_state_dict (参数)
    • 解释：load 函数要求你传入当前的 model.state_dict()。为什么？因为加载器需要知道现在的模型长什么样，才能把硬盘上的数据填进对应的坑位里。
  3. 验证 (Validation)：
    • 代码：validate_integrity_and_strict_load(...)
    • 解释：检查硬盘里的数据和现在的模型能不能对上？有没有少 key？形状对不对？
  4. 加载切分数据：
    • 代码：sharded_strategy.load(...)
    • 解释：这是最重的一步。根据策略，每个 GPU 去硬盘里读取属于自己的那一部分权重。
  5. 合并：
    • 代码：merge(common_state_dict, loaded_state_dict)
    • 解释：把公共数据和切分数据合二为一，返回给用户。

✅ Task 5: 其他辅助功能

目标：了解文件里剩下的那些小函数是干嘛的。

  • load_tensors_metadata:
    • 只读“目录”，不读“内容”。用来快速查看检查点里有哪些 Tensor，形状是多少，而不把几百 GB 的数据读进内存。
  • load_plain_tensors:
    • 把分布式的检查点，像普通 Tensor 一样读出来（通常用于转换模型格式或者调试）。

总结 (Takeaway)

一句话概括这个文件： 它是一个调度员。它不负责底层的“写文件”操作（那是 Strategy 的事），也不负责定义模型结构。它负责协调所有 GPU，有序地将巨大的模型拆解保存，或者从碎片中组装读取。

你可以尝试这样阅读代码： 1. 先看 def save: 关注它是如何把 sharded_state_dict 拆分成 common 和 sharded 两部分的。 2. 再看 def load: 关注它是如何利用传入的 sharded_state_dict 作为“向导”来加载数据的。
