这份文件其实不是代码，也不是一篇需要阅读的文章。

它是一个“报修单模板”（Bug Report Template）。

想象一下，你在使用一个叫 Megatron-LM（这是一个非常有名的训练大模型的软件）的开源项目。当你发现它坏了、报错了，你想告诉开发者“这里有个Bug”，开发者不希望你随便发一句“软件坏了”，因为这无法帮他们定位问题。

所以，开发者写了这个文件，规定了当你给他们提意见（Issue）时，必须填写的格式。

为了让你更容易理解，我把你当作一个“发现软件坏了的用户”，为你列一个 Todo List（任务清单）。你只需要按顺序完成这些任务，就读懂了这个文件的所有内容。

🛠️ 任务清单：如何向开发者提交一个完美的 Bug 报告

任务 0：理解这是什么（文件头部信息）

文件最上面被 --- 包围的内容是给 GitHub 网站看的设置，你不需要填，但你需要知道它的作用。 * Name (名称): BUG * About (关于): 报告一个需要关注的错误。 * Title (标题): [BUG] (系统会自动给你的标题加上这个前缀，方便分类)。

(以下是你作为用户需要填写的正文部分)

✅ 任务 1：描述发生了什么

对应原文： **Describe the bug** * 你的动作： 用简洁清晰的语言写下你遇到的问题。 * 例子： “我在训练模型时，运行到第100步程序突然崩溃了。”

✅ 任务 2：教开发者如何“重现”这个问题

对应原文： **To Reproduce** * 核心逻辑： 如果开发者在他的电脑上没法让错误再次出现，他就没法修。 * 你的动作： 列出步骤 1、2、3。 * 例子： 1. 下载了数据 X。 2. 修改了配置文件 Y。 3. 运行命令 python train.py ...。 4. 看到报错。

✅ 任务 3：告诉开发者“你原本以为会发生什么”

对应原文： **Expected behavior** * 核心逻辑： 有时候你觉得是 Bug，可能是功能设计就是这样。对比“预期”和“现状”很重要。 * 你的动作： 描述正确的结果应该是什么。 * 例子： “程序应该继续训练下去，或者至少保存一个断点文件，而不是直接退出。”

✅ 任务 4：贴出“犯罪现场”的证据

对应原文： **Stack trace/logs** * 核心逻辑： 程序员需要看报错代码（红色的字）来定位是哪一行代码写错了。 * 你的动作： 复制粘贴终端里出现的那些乱七八糟的错误代码。

✅ 任务 5：交代你的“作案工具” (非常重要！)

对应原文： **Environment** * 核心逻辑： 同样的软件，在不同的电脑配置下表现不一样。开发者需要知道你的软硬件环境。 * 你的动作： 填写以下信息（原文中列出的）： * Megatron-LM commit ID: 你用的这个软件是哪个版本的？（通常是一串哈希值）。 * PyTorch version: 你用的深度学习框架版本是多少？ * CUDA version: 你的显卡驱动版本是多少？ * NCCL version: 你的多卡通信库版本是多少？

✅ 任务 6：你可以提供解决方案吗？（选填）

对应原文： **Proposed fix** * 你的动作： 如果你刚好也是个程序员，并且知道怎么修，可以在这里写出来或者贴个链接。如果不知道，这就留空。

✅ 任务 7：补充其他线索

对应原文： **Additional context** * 你的动作： 还有什么刚才没说清楚的？比如截图、特殊的硬件配置等，都可以在这里补充。

总结

这文件就是一个“问卷调查表”。

  • 对于开发者：它保证了收到的每一个 Bug 报告都包含环境、日志和重现步骤，节省沟通时间。
  • 对于你（用户）：它引导你一步步把问题说清楚，别遗漏关键信息。
