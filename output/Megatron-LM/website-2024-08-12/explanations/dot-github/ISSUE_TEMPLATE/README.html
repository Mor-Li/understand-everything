.github/ISSUE_TEMPLATE

这份 .github/ISSUE_TEMPLATE 文件夹，是整个开源项目的“智能前台接待处”。

为了让你快速理解，我们把这个项目想象成一家“大公司”（Megatron-LM），而你是来办事的“客户”。

以下是通俗易懂的解释：

1. 📁 这个文件夹 (.github/ISSUE_TEMPLATE) 主要负责什么功能？

它的功能是：“分类取号”和“填表规范”。

如果没有这个文件夹，任何用户想提意见，可能就会随口喊一句：“喂，软件坏了！”开发者根本不知道你在说什么。

有了这个文件夹，当你在 GitHub 上点击“New Issue”（提新问题）时，系统会强制把你拦下来，问你：“你是来干嘛的？报修？提建议？还是问问题？”然后根据你的选择，塞给你一张必须要填的表格。

它保证了开发者收到的每一条反馈，都是格式统一、信息齐全的。

2. 这个文件夹下的各个 📄 直接文件 分别是干什么的？

这四个文件，就是四种不同颜色的“业务申请单”：

  • 📄 bug.md（维修申请单）

    • 场景：当你发现程序报错、崩溃、无法运行时。
    • 作用：它会逼你写出“怎么坏的”、“报错代码是什么”、“你的电脑配置是什么”。
    • 一句话：“东西坏了，我要报修。”

  • 📄 enhancement.md（许愿/建议单）

    • 场景：当你觉得软件挺好用，但如果能加个“自动煮咖啡”的功能就更好了。
    • 作用：它会问你“为什么要加这个功能”、“你希望它长什么样”。
    • 一句话：“我有新想法，希望能加上。”

  • 📄 question.md（咨询登记表）

    • 场景：东西没坏，你也没新想法，就是单纯不懂怎么用。
    • 作用：它引导你清晰地把疑惑问出来，而不是去干扰修Bug的人。
    • 一句话：“我不懂怎么用，求指教。”

  • 📄 regression.md（退步/变差投诉单）

    • 场景：这是比较特殊的一种“报修”。比如上个版本跑得飞快，更新后变慢了；或者以前算得准，现在算不准了。
    • 作用：它专门用来对比“以前的数据”和“现在的数据”，帮开发者找出是哪次更新把事情搞砸了。
    • 一句话：“以前好好的，更新后反而变差了，快退回去！”

3. 子文件夹的作用是什么？

(注：在你提供的目录结构中，ISSUE_TEMPLATE 里面没有子文件夹，只有文件。但如果我们要理解它作为 .github 下的一个子文件夹的角色，可以这样理解)

  • 作为 .github/ 的子部门：
    • .github 是整个项目的“行政中心”，里面管自动化的、管安全的。
    • ISSUE_TEMPLATE 是行政中心里的“信访办”，专门专门负责处理用户来信的格式。它把杂乱无章的用户抱怨，整理成了开发者能看懂的标准文档。

4. 高层认知：一句话总结

这不是代码，这是“沟通协议”。

这个文件夹的存在，不是为了让程序跑起来，而是为了让“人和人”（用户和开发者）之间的对话效率最高。它把“怎么提问”这件事标准化了，省去了开发者反复追问“你用的什么版本？”的时间。
