tests/unit_tests/inference/test_scheduler.py

这份代码其实是在测试一个调度器（Scheduler）。

为了让你更容易理解，我们可以把这个调度器想象成一家“只有4张桌子的餐厅”。

  • max_batch_size = 4：餐厅只有4张桌子，也就是由于显存限制，GPU一次只能同时处理4个任务。
  • active_request_pool（活跃池）：正在桌子上吃饭的客人（正在被GPU计算的任务）。
  • waiting_request_pool（等待池）：在门口排队的客人。
  • completed_request_pool（完成池）：吃完饭买单离开的客人。

下面我列一个 TODO List，带你一步步看代码是如何“经营”这家餐厅的。

📋 任务清单 (Task To-Do List)

  1. 开业准备：初始化调度器，确保餐厅里没人。
  2. 客满测试：连续来4个客人，确保他们都坐下了。
  3. 排队测试：第5个客人来了，确保他被安排去排队。
  4. 翻台测试（部分完成）：有几桌吃完了，确保排队的人补位进来。
  5. 打烊测试（全部完成）：剩下的所有人吃完，确保餐厅清空。

逐步讲解 (Step-by-Step)

1. 开业准备 (Initialization)

代码对应：setup_method

self.max_batch_size = 4
self.scheduler = Scheduler(max_batch_size=self.max_batch_size)
# 检查：活跃池、等待池、完成池都必须是空的
assert len(self.scheduler.active_request_pool) == 0
assert len(self.scheduler.waiting_request_pool) == 0
assert len(self.scheduler.completed_request_pool) == 0
  • 观点：系统刚启动时，里面必须是干干净净的，没有任何残留任务。

2. 客满测试 (Fill the Batch)

代码对应：test_scheduler 中的 for 循环

# 循环4次（也就是max_batch_size）
for i in range(self.max_batch_size):
    self.scheduler.add_request(prompt, prompt_tokens, inference_parameters)
    # 检查：每加一个，活跃池里就多一个。加到4个时，池子正好满了。
    assert len(self.scheduler.active_request_pool) == i + 1
  • 观点：只要没达到最大限制（4个），新来的任务应该直接进入“活跃状态”（直接开始算），不需要排队。

3. 排队测试 (Queue Logic)

代码对应：循环后的 add_request

# 第5个任务来了
self.scheduler.add_request(prompt, prompt_tokens, inference_parameters)

# 检查：活跃池已经满了（4个），所以等待池里应该有1个任务
assert len(self.scheduler.waiting_request_pool) == 1

# 检查：这个等待的任务，状态必须标记为“排队中 (WAITING_IN_QUEUE)”
waiting_request = list(self.scheduler.waiting_request_pool.values())[0]
assert waiting_request.status == Status.WAITING_IN_QUEUE

# 检查：调度器现在确实有任务在处理或等待
assert self.scheduler.have_requests_pending()
  • 观点：一旦超过最大并发量（4个），新任务必须被扔进“等待池”。

4. 翻台测试 (Update & Rotation)

这是最关键的一步。代码模拟了部分任务完成，调度器进行“更新”。

active_request_dict = self.scheduler.active_request_pool
# 模拟：把 ID 是偶数的任务标记为“已完成 (COMPLETED)”
# 假设 ID 是 0, 1, 2, 3。那么 0 和 2 完成了，1 和 3 还在做。
for request_id, request in active_request_dict.items():
    if int(request_id) % 2 == 0:
        request.status = Status.COMPLETED

# 动作：调度器更新池子（打扫桌子，叫号）
self.scheduler.update_requests_pools(active_request_dict)

# 检查：
# 1. 之前完成了2个，空出2个位置。
# 2. 排队的那1个（第5个任务）补位进来了。
# 3. 所以现在活跃池里有：任务1、任务3、任务5。共 3 个。
assert len(self.scheduler.active_request_pool) == 3

# 检查：等待池空了（因为唯一的那个排队的已经进去了）
assert len(self.scheduler.waiting_request_pool) == 0

# 检查：完成池里有2个（任务0和任务2）
assert len(self.scheduler.completed_request_pool) == 2
  • 观点：update_requests_pools 这个函数负责把“完成的任务”移走，并把“等待的任务”填补到空缺的位置上。

5. 打烊测试 (Cleanup)

代码对应：最后一段

# 模拟：把现在活跃池里剩下的3个任务全部标记为“已完成”
for request_id, request in active_request_dict.items():
    request.status = Status.COMPLETED

# 动作：再次更新
self.scheduler.update_requests_pools(active_request_dict)

# 检查：活跃池空了
assert len(self.scheduler.active_request_pool) == 0
# 检查：等待池空了
assert len(self.scheduler.waiting_request_pool) == 0
# 检查：完成池里现在有全部5个任务
assert len(self.scheduler.completed_request_pool) == 5

# 检查：调度器里彻底没任务了
assert self.scheduler.have_requests_pending() == False
  • 观点：所有任务处理完后，系统应该回到空闲状态，所有任务都应归档到完成池。

总结

这个文件的核心观点就是验证 Megatron 的推理调度器 是否具备以下能力： 1. 并发控制：不超过设定的最大显存/计算负载（max_batch_size）。 2. 排队机制：超载时能正确缓存请求。 3. 动态调度：一旦有资源释放（任务完成），能立刻自动把排队的任务拉进来处理。
