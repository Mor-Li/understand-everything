.gitlab-ci.yml

这份文件是一个 GitLab CI/CD 配置文件。你可以把它想象成一个自动化流水线的说明书。每当你提交代码（或者有人合并代码、定时任务触发）时，GitLab 就会照着这份说明书，指挥服务器去干活。

这份流水线主要属于 NVIDIA Megatron-LM 相关的项目（深度学习模型训练框架），因为它涉及大量的 GPU 环境配置、Docker 镜像构建和 PyTorch 测试。

为了让你看懂，我把它拆解成一个 6步走的 Task List（任务清单），不仅告诉你它在干嘛，还告诉你为什么要这么干。

📝 Task 1: 搞清楚“什么时候干活” (Workflow & Rules)

目标：阅读文件开头的 workflow 部分，理解流水线在什么情况下会被触发。

  • 逻辑解读：
    • 合并请求 (Merge Request) + 标签：如果你提交了合并请求，并且打上了 Run tests 或 Run tests and nightly 的标签，流水线就会运行，并且会设置一个叫 JET_CUSTOM_FILTER 的变量（用来决定具体跑哪些测试）。
    • 定时任务 (Schedule)：如果是定时的（比如每晚），也会跑。
    • Web 触发：如果在网页上点“运行”，也会跑。
    • 主分支 (Main/Default Branch)：代码合入主分支时，也会跑。
    • 特殊规则：如果已经有一个合并请求（MR）开着，那么普通的“分支提交”就不会触发流水线（避免重复浪费资源）。

📝 Task 2: 准备“全局配置” (Variables & Stages)

目标：阅读 stages 和 variables，了解整个工程的步骤和环境。

  • 步骤 (Stages)：流水线分四步走：
    1. build (构建环境/镜像)
    2. unit_tests (单元测试)
    3. functional_tests (功能测试 - 虽然这里没直接写 job，但后面引用的文件里有)
    4. publish (发布包)
  • 变量 (Variables)：
    • 定义了 Docker 镜像的地址（CI_MCORE_IMAGE 等）。
    • 定义了默认超时时间（10小时）。
    • 定义了集群名称（SLURM_CLUSTER），这是 NVIDIA 内部的高性能计算集群（dgxa100 或 dgxh100）。

📝 Task 3: 预检与资源盘点 (Pre-check)

目标：看懂 metadata 和 ppp_capacity_statistics 这两个任务。它们在正式干活前运行（.pre 阶段）。

  1. metadata 任务：
    • 它根据你选择的集群（EOS 还是 Draco），自动决定一个环境变量 JET_CI_BRANCH。
    • 把这个变量保存到 build.env 文件里，供后面的任务使用。
  2. ppp_capacity_statistics 任务：
    • 这是一段比较复杂的脚本。它的作用是查水表。
    • 它调用 API 去检查计算集群（Slurm）的资源配额（Quota）和当前使用量。
    • 目的：看看剩下的计算资源还够不够。它只打印信息（echo），告诉你“预算/资源还剩多少”，主要用于监控，防止资源耗尽导致任务卡死。

📝 Task 4: 造轮子——构建镜像 (Build)

目标：看懂 build_image 任务。这是 build 阶段的核心。

  • 并行构建 (Matrix)：它同时构建三个不同的 Docker 镜像：
    • CI_MCORE_IMAGE: 核心运行环境。
    • CI_NEMO_IMAGE: 配合 NeMo 框架的环境。
    • LINTING_IMAGE: 用来检查代码格式的环境。
  • 缓存机制：
    • 它会先检查有没有旧镜像（Cache），如果有就利用起来，加快构建速度。
    • 构建完后，它会把镜像推送到仓库（docker push）。
  • 打标签：如果是主分支或特定版本分支，它会给镜像打上特殊的标签（Tag），方便后续引用。

📝 Task 5: 质检——运行测试 (Unit Tests)

目标：这是最长的一块，包含 unit_tests 开头的各种任务。

  1. 通用配置 (.unit_test_common)：
    • 所有测试任务都继承这个配置。
    • 硬件：必须在 8xL40S 这种高端 GPU 节点上运行。
    • 环境：使用刚才构建好的 Docker 镜像。

  2. 具体测试任务：

    • unit_tests (主任务)：跑核心单元测试，并生成代码覆盖率报告（Coverage）。
    • unit_tests-data, unit_tests-fusions, unit_tests-models 等：
      • 这些是将测试拆分运行。
      • 注意规则 (Rules)：如果是在合并请求（MR）里且打了 Run tests 标签，这些拆分的任务不跑（when: never），可能只跑主任务。反之，在某些情况下它们会默认运行。
    • formatting: 检查代码风格是否符合规范（Linting）。
    • docs_build_test: 尝试构建文档，确保文档没写坏。

  3. 补充：文件末尾有一句 include: - jet-tests.yml。这意味着还有一部分测试逻辑（可能是更复杂的集成测试）写在 jet-tests.yml 这个外部文件里，被引入进来了。

📝 Task 6: 发货——打包发布 (Publish)

目标：看懂最后的 publish-wheel 任务。

  • 触发条件：只有在分支名以 core_r 开头（发布分支），并且手动设置变量 PUBLISH 为 "yes" 时，才会出现“手动点击”按钮（when: manual）。平时是不会跑的。
  • 做什么：
    • 安装打包工具 (twine, build)。
    • 构建 Python 的 .whl 安装包（兼容 Python 3.10 和 3.11）。
    • 修复包的依赖 (auditwheel repair)。
    • 最后上传到 PyPI 仓库（让别人能 pip install）。

总结 (Summary)

如果把这个流程比作做菜：

  1. Workflow: 老板下单（提交代码），看单子上有没有备注（Label），决定接不接单。
  2. Pre-check: 看看厨房煤气够不够（资源配额），确定是用哪个灶台（集群环境）。
  3. Build: 备菜。切菜、洗菜，准备好半成品（构建 Docker 镜像）。
  4. Unit Tests: 试吃。分好几个试吃员，有的尝咸淡（Linting），有的尝核心味道（Unit Test），用的都是高级餐具（8xL40S GPU）。
  5. Publish: 装盘上桌。只有在确定是正式宴席（Release分支）且老板确认（Manual）时，才打包送给客人（PyPI）。
