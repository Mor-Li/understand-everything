.github/workflows/label_issue.yml

没问题。这段代码其实是一个 GitHub Action（自动化脚本）。你可以把它想象成一个专门负责给新问题（Issue）贴标签的机器人。

为了让你彻底搞懂，我们把阅读这段代码的过程变成一个 “拆解任务清单” (Todo List)。我们一步一步来完成这个清单。

📋 任务清单：拆解自动化脚本

✅ 任务 1：搞清楚“它在什么时候干活？” (Trigger)

代码位置：

on:
  issues:
    types:
      - opened

解读： * 这是机器人的启动开关。 * 含义： 只有当有人在仓库里 “新提交了一个 Issue（问题）” (opened) 的时候，这个脚本才会醒过来开始工作。如果是修改旧问题或评论，它不会理会。

✅ 任务 2：搞清楚“它需要什么权限？” (Permissions)

代码位置：

    permissions:
      issues: write

解读： * 这是机器人的工作证。 * 含义： 既然要给 Issue 贴标签，它就必须有修改 Issue 的权限 (write)。没有这一行，它想贴标签会被系统拦住。

✅ 任务 3：搞清楚“它的核心大脑怎么想的？” (Logic)

这是最长的那段 run: | 下面的代码。这是脚本的逻辑核心。我们把它拆解成几个小步骤：

步骤 3.1：准备环境

env:
  ISSUE_TITLE: ${{ github.event.issue.title }}
  • 解读： 机器人先把刚才用户提交的那个 Issue 的标题拿到了，存起来备用。

步骤 3.2：定义“关键词” (Keywords)

NPU_KEYWORDS=(npu huawei ascend 华为 昇腾 910)
  • 解读： 机器人手里拿了一张清单。它心里想：“如果标题里出现了这些词，我就要给它贴上 npu 的标签。”
  • 关键词包括：npu, huawei (华为), ascend (昇腾), 910 (一款芯片型号) 等。

步骤 3.3：统一格式 (Normalization)

ISSUE_TITLE_LOWER=$(echo $ISSUE_TITLE | tr '[:upper:]' '[:lower:]')
  • 解读： 机器人很严谨。为了防止有人写 "HUAWEI" 而有人写 "huawei"，它先把标题里所有的英文字母都变成了小写。这样比对起来更准确。

步骤 3.4：开始侦探工作 (Loop & Check)

for KEYWORD in ${NPU_KEYWORDS[@]}; do
  if [[ $ISSUE_TITLE_LOWER == *$KEYWORD* ]] && [[ $ISSUE_TITLE_LOWER != *input* ]]; then
    LABEL="npu"
    break
  fi
done
  • 解读： 这是最关键的逻辑！机器人开始拿放大镜检查标题了。
  • 它会拿清单里的每一个词（比如“华为”）去跟标题比对。
  • 判断条件（必须同时满足）：
    1. 标题里包含这个关键词（比如包含了“华为”）。
    2. 并且，标题里不包含 "input" 这个词。（这可能是一个特殊的业务规则，也许带有 input 的标题属于另一类问题，不需要贴 NPU 标签）。
  • 结果： 如果满足条件，机器人就在心里记下：LABEL="npu"（我要贴 npu 标签），然后停止检查 (break)。

✅ 任务 4：搞清楚“它最后做了什么动作？” (Action)

代码位置：

if [ -n "$LABEL" ]; then
  gh issue edit $ISSUE_URL --add-label $LABEL
fi
  • 解读： 机器人最后检查一下自己手里有没有标签（if [ -n "$LABEL" ]）。
  • 如果有（即刚才匹配成功了），它就执行命令 gh issue edit ... --add-label。
  • 动作： 也就是在那个 Issue 页面右侧的 Labels 栏里，自动贴上一个 "npu" 的标签。

📝 总结：这个文件讲了个什么故事？

如果把这个文件翻译成人话，就是告诉 GitHub 的服务器：

“嘿，听着！只要有人新提交了一个 Issue，你就给我派个机器人过去。

让机器人看看这个 Issue 的标题。

如果标题里提到了 ‘华为’、‘昇腾’、‘NPU’ 这些词，而且标题里没有 ‘input’ 这个词，

就自动给这个 Issue 贴上一个 ‘npu’ 的分类标签。”

目的： 为了自动分类，省得管理员以后一个个手动去给关于华为/昇腾芯片的问题贴标签。
