examples/kt_optimize_rules/DeepSeek-V3-Chat-sft-amx-multi-gpu-4.yaml

这份文件其实是一个 “施工图纸” 或者 “调度指令”。

它的背景是：你想运行 DeepSeek-V3 这样巨大的模型，但单个显卡显存不够，或者你想利用 CPU 来加速/省显存。你需要用 ktransformers 这个工具，指挥 4 张显卡（GPU）和 CPU 协同工作。

这个 YAML 文件的作用就是告诉程序：模型的哪一部分放在哪张卡上，哪一部分扔给 CPU 算。

为了让你听懂，我把这个配置文件的逻辑拆解成一个 “项目经理的 To-Do List”，我们一步步来看：

📋 项目经理的调度清单 (To-Do List)

Task 1: 准备工作 (处理词表)

  • 目标：处理模型的“字典”（Embedding 层）。
  • 指令：model.embed_tokens -> 放 CPU。
  • 白话：最开始把文字转成数字的那一步，不占宝贵的显卡资源，直接在 CPU 上做。

Task 2: 划分地盘 (切分模型层数)

这是文件最核心的逻辑。DeepSeek-V3 模型像千层饼一样，一共有 61 层（Layer 0 到 Layer 60）。文件把它们切成了 4 段，分给 4 张显卡接力跑（这叫流水线并行）： * 分工： * GPU 0: 负责第 0 ~ 14 层。 * GPU 1: 负责第 15 ~ 29 层。 * GPU 2: 负责第 30 ~ 44 层。 * GPU 3: 负责第 45 ~ 60 层。

Task 3: 改造零件 (替换算子)

为了跑得快，不能用原本慢吞吞的计算方式，要换成 ktransformers 特制的“加速零件”。 * 位置编码 (Rotary Embedding)：换成 YarnRotaryEmbeddingV3。 * 线性层 (Linear Layers)：换成 KTransformersLinear。 * 注意力机制 (Self-Attention)：换成 KDeepseekV2Attention。 * MoE 门控 (Gate)：换成 KMoEGate。 * 白话：这些都是常规操作，就是告诉每一张显卡：“在你负责的层数里，用这些优化过的工具来算，别用原生的。”

Task 4: 处理最占内存的大胖子 (MoE Experts) 🔥重点

DeepSeek-V3 是 MoE（混合专家）模型，它的“专家参数”非常巨大，显存根本塞不下。 * 指令：KSFTExpertsCPU，后端使用 AMXInt8。 * 策略： * Prefill (阅读提问时)：为了快，尽量用 GPU 硬算。 * Generate (生成回答时)：显卡显存不够了，把计算任务扔给 CPU 去跑。 * 优化：使用了 AMXInt8，这是英特尔 CPU 的一种加速指令集。 * 白话：这是这个配置文件的精髓。它在说：“计算量最大的那部分（Experts），生成的时候全扔给 CPU 去算，利用 CPU 的大内存和 AMX 加速，别把显卡撑爆了。”

Task 5: 建立交通指挥 (Transfer Map)

因为模型分在了 4 张卡上，数据需要“接力”。 * 指令：model -> transfer_map。 * 规则： * 算完第 14 层 -> 把数据传给 GPU 1。 * 算完第 29 层 -> 把数据传给 GPU 2。 * 算完第 44 层 -> 把数据传给 GPU 3。 * 白话：就像接力赛跑，规定好谁跑哪一棒，跑完把接力棒扔给谁。

Task 6: 收尾工作 (输出层)

  • 目标：最后把数字转回文字（LM Head）和标准化（Norm）。
  • 指令：lm_head 和 model.norm -> 放 GPU 3。
  • 白话：最后一张显卡（GPU 3）跑完最后一层后，顺便把最终结果算出来。

💡 总结：这个文件到底干了啥？

一句话总结： 这是一个“4卡 GPU + CPU 混合推理”的方案。

它的运行流程是这样的： 1. CPU 处理输入的字。 2. GPU 0 算前 15 层（如果不含 MoE 大参数，它自己算；遇到大参数，扔给 CPU 算完再拿回来）。 3. 数据传给 GPU 1，算中间 15 层（同上，大参数扔给 CPU）。 4. 数据传给 GPU 2，算后面 15 层。 5. 数据传给 GPU 3，算最后 16 层，并输出结果。

为什么要这么做？ 为了在有限的显存下（比如你没有 8 张 H100），通过压榨 CPU 的内存和算力（AMX），强行跑起来 DeepSeek-V3 这种超级大模型。
