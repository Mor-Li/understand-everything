src/llamafactory/webui/runner.py

这份代码 src/llamafactory/webui/runner.py 是 LLaMA-Factory WebUI 的核心调度员。

简单来说，它的作用是：连接网页界面（前端）和后台训练程序（后端）。当你点击网页上的“开始训练”按钮时，就是这个 Runner 类在干活。

为了让你更容易理解，我们可以把 Runner 想象成一个 “包工头”，他手里有一张 “任务清单 (Todo List)”。每当你发起一个请求，他就按照这个清单一步步执行。

下面我为你列出这个 List，并逐步讲解每个步骤在代码里对应做了什么。

📋 Runner 的任务清单 (Todo List)

  1. 检查工作环境 (初始化与校验)
    • 任务： 确认用户填没填模型路径？选没选数据集？
  2. 翻译需求 (参数解析)
    • 任务： 把用户在网页上点的按钮、填的数字，翻译成训练程序能看懂的各种参数。
  3. 预演方案 (预览命令)
    • 任务： 不真跑，只是把生成的命令打印出来给用户看一眼。
  4. 开工干活 (启动进程)
    • 任务： 真正启动后台的训练程序 (llamafactory-cli)。
  5. 现场监工 (监控进度)
    • 任务： 盯着后台程序，把它的日志（Log）和进度条实时传回给网页显示。
  6. 收尾工作 (清理与完成)
    • 任务： 训练完了或者出错了，清理内存，告诉用户结果。
  7. 存档与读档 (配置管理)
    • 任务： 保存当前的设置，或者加载以前的设置。

逐步详细讲解

1. 检查工作环境 (初始化与校验)

  • 对应代码： _initialize 方法
  • 他在做什么： 在你点击开始之前，Runner 得先看看能不能跑。
    • 如果你没选模型 (model_name)，报错。
    • 如果你没选数据集 (dataset)，报错。
    • 如果是训练模式，还没给输出路径 (output_dir)，报错。
    • 如果是演示模式 (demo_mode)，可能禁止你乱跑训练。
    • 目的： 防止还没开始跑就因为缺参数直接崩溃，给用户友好的提示。

2. 翻译需求 (参数解析)

  • 对应代码： _parse_train_args (训练用) 和 _parse_eval_args (评估用)
  • 他在做什么： 网页上是一个个下拉框和输入框（比如 top.finetuning_type, train.learning_rate）。但后台的训练脚本需要的是一个标准的 Python 字典或者命令行参数。
    • 这个方法把网页上的 data（一堆组件的值）提取出来。
    • 它会处理很多细节，比如：
      • 如果你选了 LoRA，它会把 lora_rank 等参数加进去。
      • 如果你选了 FlashAttention2，它会设置 flash_attn="fa2"。
      • 如果你启用了 DeepSpeed，它会去加载对应的配置文件。
    • 目的： 生成一份详尽的配置清单（args 字典），准备传给训练核心。

3. 预演方案 (预览命令)

  • 对应代码： _preview -> preview_train / preview_eval
  • 他在做什么： 用户可能想知道：“我点了这么多按钮，到底最后执行的是什么命令？”
    • 它先调用 _initialize 检查错误。
    • 然后调用 _parse_train_args 拿到参数字典。
    • 最后用 gen_cmd(args) 把字典转换成一行长长的 Shell 命令字符串。
    • 目的： 显示在网页的输出框里，方便高级用户检查或复制去终端运行。

4. 开工干活 (启动进程)

  • 对应代码： _launch -> run_train / run_eval
  • 他在做什么： 这是最关键的一步。
    • 它会创建一个新的文件夹（output_dir）。
    • 它会把当前的配置保存成文件（方便以后复现）。
    • 核心动作： self.trainer = Popen(["llamafactory-cli", "train", ...])
      • 这行代码相当于在后台开了一个新的终端窗口（子进程），执行 llamafactory-cli 命令。
      • 使用 Popen 是为了不让网页卡死，训练在后台跑，网页在前台还能动。

5. 现场监工 (监控进度)

  • 对应代码： monitor
  • 他在做什么： 后台程序跑起来了，Runner 不能闲着，它得实时汇报。
    • 这是一个 Generator (生成器)，它会不断地“产出”数据给网页更新。
    • 它在一个 while 循环里，不断检查后台进程 self.trainer 的状态。
    • 获取信息： 调用 get_trainer_info 读取日志文件。
    • 更新UI： 把最新的日志文本、进度条的变化、Loss 曲线图的数据，打包 yield 给前端 Gradio 界面。
    • 处理中断： 如果用户点了“中止”，它会显示“正在中止...”。

6. 收尾工作 (清理与完成)

  • 对应代码： _finalize 和 set_abort
  • 他在做什么：
    • 正常结束： 循环结束，显示“Finished”。
    • 异常结束： 如果后台进程报错（Return code != 0），它会把错误信息（stderr）打印出来给用户看。
    • 用户强制停止： 如果用户点了停止，调用 set_abort -> abort_process 杀掉后台进程。
    • 最后调用 torch_gc() 清理显存，把 Runner 的状态重置为“空闲”。

7. 存档与读档 (配置管理)

  • 对应代码： save_args, load_args, check_output_dir
  • 他在做什么：
    • 保存： 把当前网页上填的所有内容，保存成一个 JSON 配置文件。
    • 加载： 从 JSON 文件读取配置，自动填回网页的输入框里。
    • 断点恢复检查 (check_output_dir)： 如果你填了一个已经存在的输出目录，它会警告你，并尝试加载那个目录下之前的训练配置，方便你继续训练（Resume）。

总结

这段代码的核心逻辑流就是：

  1. UI 输入 (用户点点点) ⬇️
  2. 校验与解析 (Runner 把 UI 变成参数字典) ⬇️
  3. 启动子进程 (Runner 召唤 llamafactory-cli 在后台干活) ⬇️
  4. 循环监控 (Runner 盯着子进程，把日志搬运回 UI) ⬇️
  5. 结束清理 (释放资源)

你看不懂的原因可能是被大量的参数判断（if get("...") ...）给淹没了。其实那些只是在做“填表”的工作，核心机制就是上面这 5 步。
