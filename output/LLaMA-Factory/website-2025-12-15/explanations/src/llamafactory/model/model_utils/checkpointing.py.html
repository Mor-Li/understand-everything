src/llamafactory/model/model_utils/checkpointing.py

这个文件看起来很复杂，是因为它涉及到了深度学习训练中最底层的显存优化（Memory Optimization）和数值稳定性（Numerical Stability）技巧。

简单来说，这个文件的核心目的是：在训练大模型时，想尽办法省显存，同时保证模型别练崩了。

为了让你看懂，我把这个文件要做的事情拆解成一个 “大模型训练前的准备清单 (Task Todo List)”。我们像包工头一样，一步步看代码是怎么完成这些任务的。

任务清单 (Task Todo List)

Task 1: 显存不够怎么办？开启“梯度检查点” (Gradient Checkpointing)

背景： 训练大模型时，中间产生的临时数据（Activations）非常占显存。 传统做法： 把所有中间数据都存着，等着反向传播用。结果：显存爆炸（OOM）。 省钱做法（梯度检查点）： 中间数据我不存了，算完就扔。等反向传播需要用的时候，我再重新算一遍。虽然慢了一点点，但显存省了一大半。

  • 代码对应： _gradient_checkpointing_enable 函数。
  • 动作： 这个函数会把模型原本的机制替换掉，强制开启这个省显存模式。

Task 2: 显存还是不够怎么办？用“Unsloth”的黑科技 (Offload to CPU)

背景： 即使开了上面的功能，显存可能还是紧巴巴的。 进阶做法： Unsloth 团队（一个专门做大模型优化的团队）想了个招：既然 GPU 显存贵，CPU 内存便宜，那我在存中间数据的时候，把数据暂时扔到 CPU 内存里去，等要用的时候再搬回 GPU。

  • 代码对应： get_unsloth_gradient_checkpointing_func 函数。
  • 解读：
    • forward (前向传播): 把 hidden_states 搬运到 CPU (.to("cpu"))。
    • backward (反向传播): 把数据从 CPU 搬回 GPU (.to("cuda"))，然后重新计算。

Task 3: 别做无用功，只对“能训练”的层动手 (Smart Checkpointing)

背景： 有些层是冻结的（Frozen），不需要更新参数。如果对这些层也搞“重新计算”那一套，纯属浪费时间，而且可能会干扰某些特殊的优化器（比如 BAdam）。 优化做法： 检查一下这一层是不是要训练（requires_grad）。如果要训练，我才搞检查点；如果不要训练，就按正常流程走。

  • 代码对应： get_custom_gradient_checkpointing_func 函数。
  • 解读： 它是一个装饰器（Wrapper），在执行检查点之前，先判断 if any(param.requires_grad ...)。

Task 4: 防止数学计算溢出 (Upcasting to FP32)

背景： 现在的模型为了快，通常用半精度（FP16 或 BF16）训练。但是，有些关键部位（比如 LayerNorm 层和最后的输出层）对精度非常敏感。如果用半精度，容易出现数值溢出（变成 NaN），导致训练失败。 稳健做法： 无论整体用什么精度，强制把LayerNorm和最后的输出头 (LM Head) 转成全精度（FP32）来计算。

  • 代码对应： prepare_model_for_training 函数中的逻辑。
  • 解读：
    • if model_args.upcast_layernorm: 找到所有 LayerNorm，转成 float32。
    • if model_args.upcast_lmhead_output: 给输出层挂一个钩子（Hook），强制输出 float32。

总结：代码执行流程图

当你调用 prepare_model_for_training（准备开始训练）时，代码是这样一步步执行的：

  1. 准备阶段 (prepare_model_for_training)：

    • 👋 Task 4 执行：把 LayerNorm 变成 FP32，保证稳。
    • 👋 Task 4 执行：把输出层 (LM Head) 变成 FP32，保证稳。

  2. 开启省显存模式：

    • 检查用户是不是想用 FSDP2（一种分布式训练技术），如果是，调整一下设置。
    • 如果用户没禁用梯度检查点，调用 _gradient_checkpointing_enable。

  3. 配置省显存策略 (_gradient_checkpointing_enable)：

    • ❓ 抉择：用户想用 Unsloth 的黑科技吗？
      • 是 -> 拿来 Task 2 的逻辑（存到 CPU）。
      • 否 -> 用 PyTorch 自带的逻辑（存到 GPU）。
    • 🛠 加工：不管选哪个，都套上 Task 3 的逻辑（只对训练层生效）。
    • ✅ 激活：把这一套逻辑应用到模型上。

这段代码的价值

如果你不用这段代码，直接用原生的 HuggingFace Transformers 训练： 1. 显存很容易爆（OOM）。 2. 如果你开了 LoRA 或者冻结了部分层，原生的梯度检查点可能会浪费计算资源。 3. 混合精度训练时，Loss 可能会突然变成 NaN（因为没做 FP32 强转）。

一句话总结：这是一个“大模型训练前的精细化改装车间”，目的是为了让你的显卡能跑得动更大的模型，而且跑得更稳。
