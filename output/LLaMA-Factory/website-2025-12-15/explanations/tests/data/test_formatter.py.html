tests/data/test_formatter.py

这份代码文件 (test_formatter.py) 是 LlamaFactory 项目中的一个测试文件。

简单来说，它的作用是确保 LlamaFactory 能够正确地把“人类语言”和“工具（函数）定义”转换成不同 AI 模型（如 Llama3, Qwen, Mistral）能够听懂的“格式”。

因为不同的模型“讲不同的方言”，比如 Qwen 喜欢用 XML 标签 <tool_call>，而 Llama 3 喜欢用 JSON 格式。这个文件就在测试：代码生成的格式对不对？

为了让你看懂，我把你（作为开发者）需要理解的逻辑拆解成一个 Task List (任务清单)，然后一步步讲解。

📋 你的学习任务清单 (Task To-Do List)

  1. 准备数据 (Setup): 定义好“假”的工具和函数数据，用来做测试素材。
  2. 基础对话测试 (Basic Chat): 测试最简单的“人说话 -> AI 回答”格式。
  3. 告知 AI 有哪些工具 (Tool Prompting): 测试如何把工具列表（API 文档）塞进 Prompt 里告诉 AI。
  4. 模拟 AI 调用工具 (Function Call Formatting): 测试当 AI 决定使用工具时，生成的文本应该长什么样（用于训练数据）。
  5. 解析 AI 的回答 (Tool Extraction): 测试当 AI 真的输出了一段调用工具的文本，代码能不能把它提取出来变成程序能运行的指令。
  6. 多模型适配 (Model Dialects): 验证上述逻辑在不同模型（Llama3, Qwen, Mistral, GLM4）上是否符合各自的官方规范。

🚀 逐步讲解 (Step-by-Step)

1. 准备数据 (Setup)

代码最开头定义了一些常量，这是测试用的“假数据”。 * FUNCTION: 模拟 AI 决定调用某个工具时的具体内容（名字叫 tool_name，参数是 foo="bar"）。 * TOOLS: 模拟在这个对话场景下，一共提供了哪些工具给 AI 选（比如这是一个查询天气的工具描述）。

2. 基础对话测试 (Basic Chat)

对应代码: test_string_formatter * 场景: 普通聊天，不涉及工具。 * 逻辑: 这里的 StringFormatter 负责把对话拼成特定格式。 * 测试点: 输入 "Hi"，代码是否将其包装成了 ["<s>", "Human: Hi\nAssistant:"]。这是最基础的微调数据格式。

3. 告知 AI 有哪些工具 (Tool Prompting)

核心概念: 如果你要 AI 使用工具（比如查天气），你必须先在 System Prompt（系统提示词）里告诉它：“你可以使用以下工具...”。 对应类: ToolFormatter 的 apply 方法。

  • 通用版 (test_default_tool_formatter):
    • 测试系统生成的 Prompt 是否包含 "You have access to the following tools..." 以及工具的详细描述。
  • Qwen 版 (test_qwen_tool_formatter):
    • Qwen 模型比较特别，它要求工具定义放在 XML 标签 <tools>...</tools> 里。测试代码就在检查生成的字符串里有没有这些标签。
  • Llama3 版 (test_llama3_tool_formatter):
    • Llama3 要求 Prompt 里写 "Cutting Knowledge Date..." 并且工具描述要用 JSON 格式。

4. 模拟 AI 调用工具 (Function Call Formatting)

核心概念: 在训练阶段，我们需要给模型看正确的“答案”。如果用户问“天气如何”，正确的答案不是一句话，而是一段“调用天气函数”的代码。 对应类: FunctionFormatter 的 apply 方法。

  • 场景: 假设 content 是工具调用的 JSON 数据。
  • 通用版 (test_function_formatter):
    • 期望输出格式是：Action: tool_name\nAction Input: {...}。这是早期 ReAct 风格的格式。
  • Mistral 版 (test_mistral_function_formatter):
    • Mistral 模型要求调用工具时前面加 [TOOL_CALLS] 标记。
  • Qwen 版 (test_qwen_function_formatter):
    • Qwen 模型要求输出包裹在 <tool_call> 和 </tool_call> 之间，并且最后加 <|im_end|>。

5. 解析 AI 的回答 (Tool Extraction)

核心概念: 在推理（实际使用）阶段，模型吐出了一堆字符串。程序需要从这堆字符串里把“函数名”和“参数”抠出来，才能去执行真正的 Python 代码。 对应类: ToolFormatter 的 extract 方法。

  • 任务: 给你一段乱七八糟的文本，你能提取出 ("test_tool", "{\"foo\": \"bar\"...}") 吗？
  • 通用版 (test_default_tool_extractor):
    • 去匹配 Action: 和 Action Input: 后面的内容。
  • Llama3 版 (test_llama3_tool_extractor):
    • Llama3 直接输出 JSON，所以测试能不能直接解析这个 JSON。
  • 多工具调用 (test_..._multi_tool_extractor):
    • 如果 AI 一口气要调用两个工具（比如先查天气，再查机票），代码能把这两个都提取出来吗？

6. 多模型适配 (Model Dialects)

你会发现代码里有很多类似的函数名，只是中间的单词变了： * test_glm4_... (智谱 GLM-4) * test_llama3_... (Meta Llama 3) * test_mistral_... (Mistral AI) * test_qwen_... (阿里 Qwen)

这一步的观点是： 没有一种通用的“工具调用格式”。每个大模型厂商都有自己的 Prompt 最佳实践。LlamaFactory 的这个文件就是在保证：无论你用哪个模型，我们的代码都能帮你自动转换成那个模型最喜欢的格式，你不需要自己去手写这些复杂的 XML 或 JSON 拼装逻辑。

总结

这个文件其实就是在测试 “翻译机” 的功能： 1. 把 Python 的工具定义 翻译 成 模型能读懂的 System Prompt。 2. 把 模型的输出字符串 翻译 回 Python 能执行的 函数名和参数。 3. 确保这个“翻译机”对 Llama3、Qwen、Mistral 等不同语言的人都能正常工作。
