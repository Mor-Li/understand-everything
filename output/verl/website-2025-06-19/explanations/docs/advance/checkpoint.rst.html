docs/advance/checkpoint.rst

这份文档主要是在讲在大规模模型训练（RLHF）中，如何保存和恢复进度（Checkpoint），以防止机器故障导致前功尽弃，以及如何处理这些保存下来的文件。

因为它涉及了很多分布式训练（FSDP, Megatron）的技术细节，所以读起来比较晦涩。

我为你整理了一个“训练任务 To-Do List”，按照你实际操作的逻辑顺序，一步步拆解文档里的核心观点：

📋 任务清单：从训练防崩到模型导出

✅ Task 1: 理解为什么要开启 Checkpoint (存盘点)

  • 文档观点：训练过程很长，机器可能会坏，或者训练会报错。为了止损，必须开启 Checkpoint。
  • 你需要做：在配置文件里确保开启了 checkpoint 功能。
  • 细节：建议同时保存 model（模型参数）、optimizer（优化器状态）和 extra（其他状态），这样才能完美恢复训练。

✅ Task 2: 搞清楚文件存哪儿了、长什么样 (目录结构)

  • 文档观点：
    • 文件通常保存在 checkpoints/项目名/实验名/global_steps_xxx 目录下。
    • 如果你用 FSDP (PyTorch原生分布式)：文件结构比较扁平，每个 GPU rank 保存自己的部分（分片保存）。
    • 如果你用 Megatron (NVIDIA的大模型框架)：结构更复杂，会有很多层级文件夹，对应不同的并行策略（TP、PP rank）。
  • 你需要做：训练跑起来后，去对应目录看一眼，确认生成了 global_steps_... 文件夹，里面有 actor（生成模型）和 critic（评论模型）的文件夹。

✅ Task 3: 把训练好的“碎片”拼成一个完整模型 (核心功能)

  • 文档观点：训练时保存的文件是“切碎”的（分布在不同显卡上的），HuggingFace 无法直接加载。你需要用工具把它们合并。
  • 你需要做：使用脚本 scripts/model_merger.py。
  • 操作步骤：
    • 如果是 Megatron 训练的：运行 merge 命令，指定 --backend megatron。
    • 如果是 FSDP 训练的：运行 merge 命令，指定 --backend fsdp。
    • 结果：你会得到一个标准的 HuggingFace 格式模型，可以直接用于推理或发布。

✅ Task 4: (进阶) 如果模型超大，怎么加速加载？

  • 文档观点：如果你有一个巨大的 HuggingFace 模型（比如 MoE 模型）想转成 Megatron 格式进行训练，直接加载很慢。
  • 你需要做：使用 scripts/converter_hf_to_mcore.py 脚本。
  • 目的：把普通的 HF 模型预先转换成 Megatron 的分布式 Checkpoint 格式，这样训练启动时加载速度会快很多。

✅ Task 5: 了解底层的加载原理 (避免踩坑)

  • 文档观点：Verl 框架优化了加载方式。
    • 推荐方式 (Sharded Load)：每个 GPU 只加载自己需要的那部分权重，速度快，内存占用小。前提：所有计算节点必须能访问同一个共享存储（Storage Cluster）。
    • 不推荐方式 (Deprecated)：老方法是 Rank 0 读取所有权重然后广播给其他卡，容易内存溢出 (OOM)。
  • 你需要做：确保你的集群环境里，所有节点都能读取到 Checkpoint 存放的路径。

总结一下你需要关注的重点：

  1. 怕白跑 -> 开启 Checkpoint。
  2. 跑完了 -> 用 scripts/model_merger.py 把碎片文件合并成能用的 HF 模型。
  3. 模型太大启动慢 -> 用 scripts/converter_hf_to_mcore.py 预先转换格式。

这篇文档就是在教你如何管理这些文件，以及提供了对应的转换脚本工具。
