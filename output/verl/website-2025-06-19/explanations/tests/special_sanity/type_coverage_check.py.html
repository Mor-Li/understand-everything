tests/special_sanity/type_coverage_check.py

这段代码就像是一个代码作业检查员。它的主要工作是检查你在 Git 提交的新代码中，是否有足够多的类型注解（Type Annotations）。

简单来说，就是看你写代码时有没有老老实实写上 : int, : str, -> bool 这种提示，防止代码变成“天书”。

为了让你更容易理解，我把这个脚本的工作流程拆解成了一个 List (任务清单)，脚本就是按照这个顺序一步步执行的：

📋 脚本执行的 Task Todo List

Task 1: 找出哪些文件被修改了

对应代码: get_changed_files() * 动作: 脚本会对 Git 发号施令（git diff ... origin/main...HEAD）。 * 目的: 它不想检查整个项目几万行代码，它只想检查你这次修改或新增的 Python 文件。 * 结果: 拿到一个列表，比如 ['utils.py', 'model.py']。

Task 2: 找出具体修改了哪几行

对应代码: get_changed_lines(file_path) * 动作: 再次查询 Git，查看每个文件具体变动了哪里（解析 @@ 开头的 diff 信息）。 * 目的: 即使你改了一个文件，脚本也只想检查你新写的那几行代码。旧代码它不管。 * 结果: 拿到行号集合，比如 utils.py 的第 10, 11, 12 行。

Task 3: 把代码“拆解”成语法结构 (AST)

对应代码: check_file(...) 中的 ast.parse 和 ast.walk * 动作: 它不把代码当成纯文本读，而是用 Python 自带的 ast 库把它解析成“语法树”。 * 目的: 它需要知道第 10 行代码到底是一个“函数定义”，还是一个“变量赋值”，还是只是一个“注释”。 * 结果: 脚本理解了代码的结构。

Task 4: 检查有没有“类型注解” (核心逻辑)

对应代码: has_type_annotations(node) * 动作: 针对每一个修改过的语法节点，进行严格检查： * 如果是函数 (FunctionDef): * 检查参数有没有写类型（比如 arg: int）。 * 检查返回值有没有写类型（比如 -> str）。 * 注意：self 参数不需要类型。 * 如果是赋值 (Assign): * 如果赋值的是简单的常量（比如 x = 1），通常算通过（或者警告）。 * 如果是复杂的赋值，它希望看到类型。 * 结果: 给这一行代码打分：是 CHECK_SUCCESS (有注解)，还是 CHECK_FAILURE (没注解)。

Task 5: 算总分和写报告

对应代码: main() * 动作: * 统计一共改了多少行“有意义的代码”（Total Changed）。 * 统计其中有多少行是“写了类型注解的”（Total Annotated）。 * 计算比例：覆盖率 = 写了注解的行 / 总修改行。 * 目的: 看看你的代码质量达标没。 * 结果: 打印类似 🔍 Type coverage on changed lines: 5/10 = 50.00%。

Task 6: 决定是通过还是报错

对应代码: main() 结尾部分 * 动作: 对比你的分数和及格线（--threshold，默认是 0.2，也就是 20%）。 * 逻辑: * 如果覆盖率 低于 20%：脚本会抛出异常 ❌ Type coverage below threshold，导致测试失败（CI/CD 流水线通常会挂掉）。 * 如果覆盖率 高于 20%：打印 ✅ Type annotation coverage acceptable，测试通过。 * 同时，它会把所有缺失注解的行打印出来，告诉你哪一行需要改进。

总结一下文中的核心观点

这个脚本想表达的观点是： 1. 增量检查：不要试图一次性修好所有旧代码，我们只关注新提交的代码质量。 2. 类型安全：写 Python 最好带上类型注解（Type Hints），这样代码更健壮。 3. 容忍度：它没有要求 100% 的覆盖率，默认只要有 20% 的新增代码带了类型注解就算及格（这通常是一个比较宽松的“最低标准”，防止代码质量完全失控）。
