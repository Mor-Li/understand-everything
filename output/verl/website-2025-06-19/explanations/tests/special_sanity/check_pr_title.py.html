tests/special_sanity/check_pr_title.py

这份代码其实就是一个“自动化的门卫”。

它的工作场景是：当有人给项目提交代码（提 PR / Pull Request）时，这个脚本会自动运行，检查提交的标题（Title）写得规不规范。如果不规范，它就会报错，禁止提交。

为了让你更容易理解，我把它拆解成一个 Task List（任务清单），我们可以把它想象成这个脚本正在执行的一系列待办事项：

📋 脚本执行任务清单 (To-Do List)

✅ Task 1: 拿到“考生”的卷子 (获取输入)

  • 代码对应： pr_title = os.environ.get("PR_TITLE", "").strip()
  • 解释： 脚本首先从系统环境变量里把大家提交的 PR 标题 抓取出来，并去掉首尾的空格。
    • 比如：如果我提交的标题是 [doc] fix: typo，它就拿到了这段文字。

✅ Task 2: 翻开“标准答案” (定义规则)

  • 代码对应： allowed_modules = [...] 和 allowed_types = [...]
  • 解释： 脚本脑子里先背下来两份白名单：
    1. 允许的模块 (Modules)： 你修改的是哪一部分？比如是 model (模型), doc (文档), 还是 fsdp (并行策略)？如果不在这里面的词，一律不算数。
    2. 允许的类型 (Types)： 你做的是什么操作？只能是 feat (新功能), fix (修bug), refactor (重构), chore (杂事), test (测试) 这几个词之一。

✅ Task 3: 第一轮安检 —— 检查“方括号” (Check Modules)

  • 代码对应： re_modules_pattern 和 if not re_modules: 这一大段。
  • 解释：
    1. 看格式： 标题必须以 [ 开头，中间有字，然后以 ] 结尾。
    2. 看内容： 把方括号里的词拿出来（比如 [model, doc]），挨个检查是否在 Task 2 的“允许模块”名单里。
    3. 后果： 如果你写了 [abc]（不在名单里）或者没写方括号，脚本会直接报错 (raise Exception)，并告诉你：“你的模块写错了，只允许写这些……”。

✅ Task 4: 第二轮安检 —— 检查“冒号和描述” (Check Format & Type)

  • 代码对应： re_types_pattern 和 if not match: 这一段。
  • 解释：
    1. 看整体格式： 现在的要求更加严格，格式必须长这样： [模块名] 类型: 具体的描述
    2. 看类型： 冒号前面的那个词（比如 fix），必须在 Task 2 的“允许类型”名单里。
    3. 看描述： 冒号后面必须写了东西（不能是空的）。
    4. 后果： 如果你写成 [doc] fix typo (少个冒号) 或者 [doc] hello: typo (hello 不是允许的类型)，脚本会报错并拦截。

✅ Task 5: 盖章放行 (Success)

  • 代码对应： print(f"✅ PR title is valid: ...")
  • 解释： 如果上面的检查全部通过，脚本会开心地打印一个绿色的对勾 ✅，表示“标题合格，可以通过”。

💡 举个栗子 (Examples)

为了让你更直观，我们看看在这个脚本眼里，什么样的标题是合格的：

❌ 错误的标题 (会被脚本拦截): * 修复了一个bug -> 原因： 没加方括号 []。 * [unknown] fix: bug -> 原因： unknown 不是允许的模块名。 * [doc] fixed: typo -> 原因： fixed 不对，只能用 fix。 * [model] feat update -> 原因： 缺了冒号 :。

✅ 正确的标题 (脚本会放行): * [doc] fix: correct spelling -> 完美 (模块是doc，类型是fix)。 * [model] feat: add new layer -> 完美 (模块是model，类型是feat)。 * [fsdp, megatron] refactor: optimize speed -> 完美 (方括号里可以写多个模块)。

总结

这就好比你去办证件： 1. Task 1: 递交表格。 2. Task 2: 办事员拿出规章制度。 3. Task 3: 检查你的姓名（模块）是不是在户口本上。 4. Task 4: 检查你的申请类型（Type）是不是符合规定格式。 5. Task 5: 盖章通过，或者把你打回去重写。
