tests/README.md

这份文档其实是给在这个项目（verl）里写代码的程序员看的测试指南。它规定了测试代码该放哪、怎么命名、以及机器会自动运行哪些测试。

既然你觉得难懂，我们把它想象成你要入职这个项目组，这是你的入职培训任务清单（Todo List）。

请按照以下 4 个阶段来逐步理解：

第一阶段：搞清楚“东西放哪儿” (文件夹结构)

任务目标：学会如何存放你的测试代码。

  1. 普通测试：
    • 规则：测试文件夹的结构要和源代码的结构“照镜子”。
    • 例子：如果你修改了 verl/trainer 里的代码，你的测试代码就得放在 tests/trainer 里；如果是 verl/models，就放 tests/models。
  2. 特殊测试（带 special_ 前缀的文件夹）：
    • 有些测试比较特殊，不能随便放，必须放在专门的篮子里：
    • special_distributed：必须用多张显卡（Multi-GPU）才能跑的测试放这里。
    • special_e2e：端到端（End-to-End）测试。意思是模拟真实用户，从头（训练）到尾（生成）跑一遍完整流程。
    • special_npu：专门给 NPU（一种类似 GPU 的专用芯片）跑的测试。
    • special_sanity：快速健康检查。就像体检量血压一样，快速测一下系统是不是还要挂，不用跑很久。
    • special_standalone：需要在独立、隔离的环境里跑的测试。

第二阶段：搞清楚“用什么跑” (硬件分配)

任务目标：学会通过给文件起名，来控制测试是跑在 CPU 上还是 GPU 上。

  1. 默认情况（GPU）：
    • 规则：除非你特别指定，否则系统默认都会给你分配 GPU（显卡）来跑测试。
  2. 特殊情况（CPU）：
    • 规则：如果你写的测试只需要 CPU（比如只测简单的数学逻辑，不需要显卡），你必须把文件名写成以 _on_cpu.py 结尾。
    • 例子：test_math_logic_on_cpu.py -> 系统看到这个后缀，就会把它扔到 Linux 的 CPU 环境里跑。
  3. 例外：
    • 放在 special_npu 文件夹里的，当然是用 NPU 跑。

第三阶段：搞清楚“什么时候跑” (自动化工作流)

任务目标：了解当你提交代码（PR）时，GitHub 机器人（CI）会在后台自动做什么。

这部分讲的是 .github/workflows/ 里的配置文件。你可以把它们理解为机器人的自动检查清单：

  1. 必查项目（CPU Sanity）：
    • 不管你改了啥，这些都要跑：检查你的 PR 标题格式、扫描有没有泄露密码、检查文档格式等。
  2. 重型测试（Heavy Multi-GPU）：
    • 针对特定模块的大型测试，比如 model.yml（模型测试）、vllm.yml 等。这些很耗资源。
  3. 全流程测试（End-to-End）：
    • 即 e2e_*.yml，模拟完整使用场景。
  4. 单元测试（Unit Tests）：
    • 这是最杂的一项，机器人会把 tests/ 下面的文件扫一遍：
    • CPU 机器人：专门挑文件名带 _on_cpu.py 的跑。
    • GPU 机器人：跑剩下那些不带 _on_cpu.py 后缀的文件。

第四阶段：给开发者的警告 (注意事项)

任务目标：防止你把测试跑重了，浪费资源。

  • 问题背景：上面提到的“单元测试机器人”很勤快，默认会把 tests 文件夹下所有的文件都跑一遍。
  • 你的任务：
    • 如果你添加了一个新的自动化工作流（比如专门测某个新模型的 new_model.yml），并且这个测试文件也在 tests/ 目录下。
    • 一定要记得：去修改 cpu_unit_tests.yml 或 gpu_unit_tests.yml，把你的新测试文件排除（exclude）掉。
    • 为什么？ 不然“单元测试机器人”会跑一遍，你的“新模型机器人”又跑一遍，这就重复浪费了。

总结 (TL;DR)

  1. 放哪？ 普通测试跟着代码结构放，特殊的放 special_ 文件夹。
  2. 用啥跑？ 想用 CPU 跑，文件名必须加 _on_cpu.py，否则默认用 GPU。
  3. 机器人怎么测？ 分为必查的、重型的、全流程的、和普通的单元测试。
  4. 别踩坑： 如果你加了新的专门测试配置，记得告诉普通单元测试机器人：“这个我测过了，你别管了”。
