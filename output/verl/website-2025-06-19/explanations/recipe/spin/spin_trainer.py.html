recipe/spin/spin_trainer.py

这份代码是一个基于 Ray 分布式框架的 SPIN (Self-Play Fine-Tuning) 训练器的核心控制逻辑。

简单来说，SPIN 是一种让大模型“左右互搏”来自我进化的算法。这个脚本就像是一个总指挥官（Driver），它负责指挥一群工人（Workers，比如 GPU 节点）去执行生成数据、打分、计算、更新模型等任务。

为了让你看懂，我把这个脚本的核心逻辑（主要是 fit_dpo 函数）拆解成一个 Task Todo List。你可以想象这是总指挥官手里的任务清单，他按顺序一步步执行：

第一阶段：战前准备 (初始化)

在训练循环开始之前，指挥官需要先把队伍拉起来。

  1. [资源分配] ResourcePoolManager & init_workers:

    • 任务：清点 GPU 数量，把计算资源分配给不同的角色。
    • 角色：
      • Actor (演员)：负责生成文本，也是我们要训练的主模型。
      • Ref Policy (裁判/旧我)：作为参考系（Reference Model），通常是上一轮迭代的模型。
      • Reward Model (打分员)：给生成的结果打分。
    • 目的：确保每个任务都有 GPU 干活。

  2. [数据加载] _create_dataloader:

    • 任务：加载训练用的 Prompt（提示词）数据。

第二阶段：核心训练循环 (The Loop)

这是代码中最长、最核心的部分，位于 fit_dpo 函数中。SPIN 的核心思想是“在线生成数据 -> 制造胜负对 -> DPO 训练 -> 更新参考系”。

这是一个无限循环的任务清单，每一轮（Step）都要做一遍：

✅ Task 1: 进化同步 (Sync Reference Model)

  • 代码位置：if self.global_steps % ref_update_freq == 0:
  • 任务：每隔一段时间，把当前训练好的 Actor（新我） 的权重复制给 Reference Model（旧我）。
  • 观点/逻辑：SPIN 的核心在于“自我博弈”。随着训练进行，你的对手（Ref Model）必须变强，你才能继续进步。所以要定期把“最新的自己”变成“新的对手”。

✅ Task 2: 自我生成 (Generation)

  • 代码位置：self.actor_rollout_wg.generate_sequences(gen_batch)
  • 任务：指挥 Actor 拿着 Prompt 去写作文（生成回复）。
  • 目的：获取当前模型能力下的输出数据。

✅ Task 3: 结果打分 (Scoring)

  • 代码位置：self.rm_wg.compute_rm_score(batch) 或 reward_fn
  • 任务：指挥 Reward Model（或者规则函数）给刚才生成的作文打分。
  • 目的：知道哪些写得好，哪些写得烂。

✅ Task 4: 制造胜负对 (Construct Preferences)

  • 代码位置：compute_onlineDPO_pref(batch)
  • 任务：根据分数，把数据整理成 DPO 算法需要的格式。
    • 分数高的回复标记为 Chosen (胜者)。
    • 分数低的回复标记为 Rejected (败者)。
  • 观点/逻辑：这就是在线 (Online) DPO 的关键。我们不使用预先准备好的数据集，而是用模型自己刚刚生成的数据来训练自己。

✅ Task 5: 计算概率 (Compute Log Probs)

  • 代码位置：
    • self.actor_rollout_wg.compute_log_prob(batch) (当前策略的概率)
    • self.ref_policy_wg.compute_ref_log_prob(batch) (参考系策略的概率)
  • 任务：计算“当前模型”和“参考模型”生成这些回复的概率是多少。
  • 目的：DPO 损失函数需要用到这些概率值来计算梯度。它希望拉大“好回复”和“坏回复”在概率上的差距，同时不要偏离“参考模型”太远。

✅ Task 6: 准备 DPO 数据包 (Prepare Batch)

  • 代码位置：dpo_tensors = { ... }
  • 任务：把 Prompt、Chosen 回复、Rejected 回复、以及刚才算的概率打包成一个大礼包。
  • 细节：这里还会处理一下 Mask（掩码），确保只训练回复部分，不训练 Prompt 部分。

✅ Task 7: 模型更新 (Update Actor)

  • 代码位置：self.actor_rollout_wg.update_actor_dpo(dpo_update_batch_proto)
  • 任务：利用刚才的数据包，执行反向传播，更新 Actor 的权重。
  • 结果：Actor 变得更倾向于生成高分回复，避免生成低分回复。

第三阶段：后勤保障 (Housekeeping)

在每一轮循环的末尾，还需要做一些维护工作：

  1. [验证] _validate:

    • 任务：定期拿出一部分测试题，看看模型现在表现如何，是不是学歪了。
    • 输出：生成一些样板文字，记录准确率或奖励值。

  2. [存档] _save_checkpoint:

    • 任务：把训练好的模型权重保存到硬盘上，防止断电白干。

  3. [监控] logger.log:

    • 任务：把训练过程中的 Loss、Reward、长度等指标发给 WandB 或 SwanLab，画出折线图。

总结：文中的核心观点

这个脚本实际上在执行一种迭代式自我进化的策略：

  1. 不再依赖静态数据：传统的 DPO 用的是固定的数据集。这个脚本展示的是 Online DPO，数据是模型自己边跑边生成的（On-the-fly）。
  2. 动态的参考系：通过定期更新 Reference Model（Task 1），它实现了 SPIN 的理念——今天的我要打败昨天的我。
  3. Ray 的作用：因为生成（Rollout）、打分（Reward）、训练（Train）都很费显存，所以用 Ray 把这些任务拆分到不同的 GPU 甚至不同的节点上并行处理。

这就好比一个学生（Actor），每隔一周就把自己现在的水平定为及格线（Update Ref），然后做题（Generate），老师批改（Score），分析错题（DPO Update），如此循环，不断提升成绩。
