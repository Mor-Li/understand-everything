.github/workflows/check-pr-title.yml

这份文件确实容易让人困惑，因为它包含了两部分完全不同性质的内容： 1. 上半部分（带 # 的）：是一份全局说明书，它不仅仅讲这一个文件，而是讲了整个项目的测试规则。 2. 下半部分（代码）：才是这个文件真正执行的具体任务。

之所以你看不懂，大概率是因为被上半部分那一大堆和当前代码不直接相关的“说明书”给绕晕了。

为了帮你理清思路，我为你制定了一个 5步学习任务清单 (To-Do List)，我们一步步把这个文件“拆解”开来看。

✅ Task 1：搞清楚“这是什么文件？”

目标：理解文件的身份。

  • 路径：.github/workflows/check-pr-title.yml
  • 解释：这是一个 GitHub Actions 的配置文件。你可以把它想象成给 GitHub 这个“机器人”下达的指令书。
  • 作用：每当有人提交代码（Pull Request）时，GitHub 机器人就会自动读这个文件，按里面的步骤干活。

✅ Task 2：解读“全局说明书” —— 文件夹是干嘛的？

目标：读懂代码上半部分 # Tests layout 里的注释。这部分是写给开发者看的文档，告诉大家测试代码该放哪。

  • 普通测试：
    • 如果你改了 verl/trainer 里的代码，测试代码就放 tests/trainer。
    • 如果你改了 verl/models，测试就放 tests/models。
    • 观点：测试文件夹结构要和源代码结构一一对应。
  • 特殊测试（带 special_ 前缀）：
    • special_distributed：必须用多显卡跑的测试。
    • special_e2e：端到端（一条龙）测试。
    • special_npu：给 NPU（另一种芯片）用的测试。
    • special_sanity：快速健康检查（比如查查错别字、格式对不对）。
    • special_standalone：要在独立环境跑的测试。

✅ Task 3：解读“全局说明书” —— 用 CPU 还是 GPU？

目标：读懂 # Accelerators for tests 里的注释。

  • 默认规则：只要是测试，默认都给你上 GPU（显卡）。
  • 例外规则：
    1. 放在 special_npu 里的不用 GPU。
    2. 文件名规则：如果你的测试脚本文件名是以 _on_cpu.py 结尾的，系统就会强制用 CPU 跑（Linux环境）。

✅ Task 4：解读“全局说明书” —— 自动化流程有哪些？

目标：读懂 # Workflow layout 里的注释。这里列出了整个项目所有的自动化任务分类。

  1. 必跑的 CPU 检查（轻量级）：
    • 包括：检查标题格式、检查密钥泄露、生成文档等。
    • 重点：当前这个文件 check-pr-title.yml 就属于这一类！
  2. 重型多 GPU 测试：测模型、测 vLLM 等。
  3. 端到端测试 (E2E)。
  4. 单元测试 (Unit Tests)：
    • cpu_unit_tests.yml：专门跑文件名带 _on_cpu.py 的。
    • gpu_unit_tests.yml：跑其他的。

✅ Task 5：解读“实操指令” —— 这个文件到底干了啥？

目标：忽略上面的注释，只看下面的代码（on: 和 jobs: 部分）。这才是这个文件真正执行的逻辑。

  • 什么时候触发 (on)：
    • 当有人 提交 PR (pull_request) 时。
    • 具体包括：新开 PR (opened)、修改 PR (edited)、同步代码 (synchronize)。
  • 干什么活 (jobs)：
    1. 准备环境：找一台 Ubuntu 机器，装上 Python 3.11。
    2. 执行命令： yaml run: python3 tests/special_sanity/check_pr_title.py env: PR_TITLE: ${{ github.event.pull_request.title }}
    3. 翻译成人话：运行一个叫 check_pr_title.py 的 Python 脚本，并把当前 PR 的标题传给它。

总结

如果要把这个文件缩写成一句话，它的意思是：

“虽然我上面写了一大堆关于整个项目怎么做测试、怎么分 CPU/GPU 的文档（仅供参考），但我这个文件本身的功能非常简单：就是当你提交代码时，检查一下你的 PR 标题写得规不规范。”
