.github/workflows/e2e_sft.yml

这份文件是一个 GitHub Actions 的自动化测试流程配置文件。

简单来说，它的作用是：每当有人修改了代码，系统就自动启动一堆高性能显卡（GPU），模拟真实的训练过程，把“有监督微调（SFT）”这个功能从头到尾跑一遍，确保新代码没有把核心功能搞坏。

为了让你彻底看懂，我把它拆解成一个 “任务清单 (To-Do List)”，我们按顺序一步步来完成这个“自动化测试任务”。

📋 任务清单：理解 e2e_sft.yml

✅ Task 1：搞清楚“我在哪？我要测什么？” (对应文件开头的注释部分)

文件开头那一长串 # 注释，其实是给开发者看的“地图”，告诉你这个项目的测试结构是怎样的。

  • 你需要知道的点：
    • 这个文件属于 special_e2e (端到端测试) 类别。这意味着它不是测一个小函数，而是跑一个完整的训练脚本。
    • 它测试的是 SFT (Supervised Fine-Tuning)，即“有监督微调”。
    • 它属于“重量级”测试，需要用 GPU 跑。

✅ Task 2：决定“什么时候”开始干活 (对应 on: 部分)

机器资源很贵，不能随便跑。这部分定义了触发条件。

  • 触发条件：
    • 当有人 Push (推送) 代码 或者 提 Pull Request (合并请求) 到 main 分支或 v0.* 版本分支时。
  • 智能过滤 (Paths):
    • 不做： 如果你只改了文档、改了其他无关的例子 (!examples/**)，这个测试不跑（省钱）。
    • 要做： 如果你改了 .py 文件，或者专门改了 SFT 相关的核心代码（比如 fsdp_sft_trainer.py 或 e2e_sft.yml 本身），这个测试必须跑。

✅ Task 3：准备“顶级厨房” (对应 jobs: 和 container: 部分)

要跑这种 AI 模型训练，普通的电脑不行，需要配置环境。

  • 硬件： runs-on: [L20x8]。这意味着它会申请一台配有 8张 L20 显卡 的服务器。
  • 软件环境 (Docker)： 使用 verl:ngc... 这个镜像。这就像是预装好了所有锅碗瓢盆（CUDA, vLLM, PyTorch 等）的厨房。
  • 网络配置： 设置了各种代理 (HTTP_PROXY) 和 HuggingFace 的镜像地址，确保下载模型数据时不卡顿。

✅ Task 4：备菜 (对应 steps: 的前几步)

在正式炒菜（训练）之前，得先把代码拉下来，把环境装好，把菜切好。

  1. Checkout: 把你的代码下载到服务器上。
  2. Install:
    • 安装 peft (用于微调的库)。
    • 安装当前这个项目 (pip3 install ... -e .)。
  3. Prepare dataset:
    • 先杀掉可能残留的进程 (ray stop).
    • 运行 gsm8k.py。这是在下载并处理 GSM8K 这个数据集（一个常用的小学数学数据集，用来测模型逻辑的）。

✅ Task 5：花式炒菜 (对应 steps: 后面的各种 Running...)

这是文件的核心！它用同一份数据，尝试用不同的配置去跑训练，确保各种用法都没问题。

  • 第一道菜：标准做法
    • Running GSM8K E2E training tests... with rmpad
    • 运行 run_sft.sh。这是最基础的 SFT 训练测试。
  • 第二道菜：去皮做法
    • ... w/o rmpad
    • 设置 RM_PAD=False 再跑一遍。测试在不填充某些数据时的表现。
  • 第三道菜：切分做法 (序列并行)
    • ... with sequence parallism
    • 设置 SP_SIZE=2。测试把长序列切分到2张卡上处理的功能（Sequence Parallelism）是否正常。
  • 第四道菜：口味对比 (核对损失)
    • Check loss difference...
    • 运行 test_sp_loss_match.py。这步很关键：它对比“标准做法”和“切分做法”算出来的 Loss（误差）是否完全一致。如果不一致，说明并行算法写得有 Bug。
  • 第五道菜：加特技做法 (Liger Kernel)
    • ... with sequence parallism and liger
    • 设置 LIGER=True。测试开启 Liger（一种加速训练的底层优化内核）时是否会报错。
  • 第六道菜：省钱做法 (LoRA)
    • ... with LoRA
    • 设置 LORA_RANK=32。测试 LoRA（只微调少量参数）功能是否正常。

📝 总结

这个文件的逻辑就是：

  1. 有人改代码了？ -> 检查是否涉及 SFT 核心。
  2. 涉及了？ -> 开一台 8卡 GPU 服务器。
  3. 准备环境 -> 下代码、装依赖、下数据 (GSM8K)。
  4. 疯狂测试 ->
    • 普通跑一次。
    • 换个参数跑一次。
    • 开序列并行跑一次。
    • 重点： 验证并行跑的结果和普通跑是不是一样（数学上必须一致）。
    • 开底层加速跑一次。
    • 开 LoRA 跑一次。
  5. 全通过？ -> 给你的代码打个绿勾 ✅，允许合并。否则报错 ❌。
