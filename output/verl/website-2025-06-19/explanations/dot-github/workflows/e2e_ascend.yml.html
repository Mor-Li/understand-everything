.github/workflows/e2e_ascend.yml

这份文件是一个 GitHub Actions 的自动化工作流配置文件 (.github/workflows/e2e_ascend.yml)。

简单来说，它的作用是：每当你修改了代码，这个脚本就会自动在一台华为昇腾（Ascend NPU）服务器上运行一遍，确保你的代码没有把模型训练功能搞坏。

为了让你看懂，我把它拆解成三个部分：背景设定（文档注释）、触发机制（什么时候干活）、执行清单（具体干什么活）。

第一部分：背景设定（文件开头的注释）

文件最开头的注释部分（# # Tests layout ...），其实是在给开发者立规矩，告诉你这个项目的测试文件是怎么分类的。

我们可以把它看作“测试地图”：

  1. 普通测试区：
    • tests/trainer: 专门测训练器的。
    • tests/models: 专门测模型的。
  2. 特殊测试区（以 special_ 开头）：
    • special_npu: 重点！ 专门给华为昇腾 NPU 芯片用的测试（这个脚本主要就在跑这里的逻辑）。
    • special_distributed: 必须要多显卡才能跑的测试。
    • special_e2e: 端到端（End-to-End）完整流程测试。
  3. 硬件规则：
    • 默认情况下，测试都在 NVIDIA GPU 上跑。
    • 除非文件名叫 *_on_cpu.py（在 CPU 上跑）。
    • 或者在 special_npu 文件夹里（在华为 NPU 上跑）。

第二部分：触发机制（任务接单）

这部分对应代码中的 on: 和 jobs: ... container: 部分。想象这是一个机器人的“接单规则”和“装备库”。

1. 接单规则（什么时候运行？） * 规则 A (Push): 当有人把代码推送到 main 分支或者 v0.* 版本分支时，立即执行。 * 规则 B (PR): 当有人提交 Pull Request (合并请求) 到 main 分支时，且修改了以下文件时执行： * 任何 .py Python 代码。 * requirements-npu.txt (NPU 的依赖包)。 * 排除项：如果只改了 examples 或普通 tests 里的文件，通常不触发；除非改了特定的核心入口文件（如 verl/trainer/main_ppo.py 等）。

2. 装备库（在什么环境运行？） * 机器: 必须是一台自托管的（self-hosted）、代号为 npu-0 的机器。 * 容器: 运行在一个特定的 Docker 镜像里 (crispig/verl_npu...)，这个镜像里已经装好了华为的 CANN 驱动、PyTorch 和 vLLM。 * 外挂装备: 挂载了物理机的 NPU 驱动和设备（/dev/davinci0 等），这说明它是真的在用华为的 AI 芯片跑，不是模拟器。

第三部分：执行清单（Task Todo List）

这是你最关心的部分，对应代码 steps: 下面的内容。我把它转换成一个按顺序执行的 Todo List：

✅ 阶段一：环境自检与安装

  1. [检查] 确认 NPU 状态
    • 代码: npu-smi info
    • 目的: 看看华为昇腾显卡是不是活着的，驱动版本对不对。
  2. [获取] 下载代码
    • 代码: checkout@v4
    • 目的: 把你修改后的最新代码拉取到服务器上。
  3. [安装] 安装依赖包
    • 代码: pip install ... requirements-npu.txt
    • 目的: 安装运行代码所需的 Python 库，特别是针对 NPU 的依赖。
  4. [安装] 补充安装 TorchVision
    • 代码: pip install torchvision...+cpu
    • 目的: 补一个视觉库，强制指定 CPU 版本（可能为了避免版本冲突）。

✅ 阶段二：数据准备

  1. [准备] 搞定 GSM8K 数据集
    • 代码: python3 examples/data_preprocess/gsm8k.py
    • 目的: 下载并处理 GSM8K（小学数学题）数据集，为后面的训练做准备。
  2. [准备] 搞定 Geo3K 数据集
    • 代码: python3 examples/data_preprocess/geo3k.py
    • 目的: 下载并处理几何题数据集。

✅ 阶段三：实战测试（核心逻辑）

注意：每一步开始前都会运行 ray stop --force 清理内存，跑完后会删除 ckpts (模型存档) 节省空间。

  1. [测试 1] 跑 SFT (监督微调)
    • 任务: bash tests/special_e2e/sft/run_sft.sh
    • 含义: 测试最基础的 SFT 功能，看看在 NPU 上能不能正常微调模型。
  2. [测试 2] 跑 GRPO 算法 (GSM8K + Qwen2.5-0.5B)
    • 任务: bash tests/special_npu/run_qwen2_5_05b_grpo.sh
    • 含义: 用一个小一点的模型（0.5B），跑 GRPO（一种强化学习算法），验证算法逻辑在 NPU 上是否跑得通。
  3. [测试 3] 跑 GRPO 算法 (Geo3K + Qwen2.5-VL-3B)
    • 任务: bash tests/special_npu/run_qwen2_5_vl_3b_npu.sh
    • 含义: 这次上强度了，用 VL (视觉语言) 模型跑几何题。这是为了测试 NPU 对多模态模型的支持。
  4. [测试 4] 跑 DAPO 算法
    • 任务: bash tests/special_npu/run_qwen2_5_05b_dapo.sh
    • 含义: 测试另一种强化学习/对齐算法 (DAPO)，确保新算法也能跑通。

总结

这个文件的核心观点是： “要在华为昇腾 NPU 环境下，保证 verl 这个框架的核心功能（SFT、GRPO、DAPO、多模态）都能正常工作，每次代码更新都要把这套流程跑一遍。”
