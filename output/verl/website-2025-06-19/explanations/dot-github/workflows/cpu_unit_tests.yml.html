.github/workflows/cpu_unit_tests.yml

这份文件其实是一个 GitHub Actions 的配置文件。你可以把它想象成给“云端机器人”下达的一份自动化任务清单。

它的核心目的是：每当有人修改代码时，自动在只有 CPU 的环境里跑一遍测试，确保代码没改坏。

为了让你彻底看懂，我为你列了一个 学习任务清单 (Task To-Do List)，我们一步一步来拆解：

✅ Task 1: 搞懂“背景设定” (对应文件开头的注释)

目标：知道这个项目里的测试文件是怎么存放的。

文件开头的注释部分（# # Tests layout 到 # # Workflow layout）其实是写给开发者看的“地图”。

  1. 普通测试：放在 tests/ 目录下。
    • 比如 tests/trainer 测训练功能，tests/models 测模型功能。
  2. 特殊测试：放在以 special_ 开头的文件夹里。
    • special_distributed: 需要多张显卡才能跑的。
    • special_npu: 给华为 NPU 芯片跑的。
    • special_e2e: 端到端（End-to-End）完整流程测试。
  3. 硬件规则：
    • 默认情况下，测试都假设有 GPU（显卡）。
    • 重点来了：如果文件名以 _on_cpu.py 结尾，说明这个测试专门用来在 CPU 上跑（也就是本文件要管的事）。

✅ Task 2: 搞懂“分工策略” (对应 Workflow layout 注释)

目标：知道这个文件在整个测试体系里扮演什么角色。

注释里解释了 GitHub 里的几个“监工”分别管什么： 1. 轻量级检查：查标题、查密钥泄露（check-pr-title.yml 等）。 2. 重型测试：多显卡测试（model.yml 等）。 3. 端到端测试：e2e_*.yml。 4. 单元测试 (Unit Tests)： * gpu_unit_tests.yml: 跑那些需要显卡的代码。 * cpu_unit_tests.yml (就是当前这个文件): 专门跑文件名里带 _on_cpu.py 的代码。

✅ Task 3: 搞懂“触发开关” (对应 on: 部分)

目标：知道这个任务什么时候会自动开始。

看代码中的 on: 部分： * Push (推送): 当你把代码推送到 main 分支或者 v0.* 版本分支时，自动运行。 * Pull Request (提代码合并请求): * 当你请求合并到 main 或 v0.* 时。 * 且 你修改的文件是 .py 结尾的（Python代码）。 * 且 你修改的不是 recipe/ 文件夹里的东西（!recipe/**/*.py 表示排除）。

✅ Task 4: 搞懂“执行环境” (对应 jobs: 开头部分)

目标：知道机器人在什么样的电脑上干活。

  • runs-on: ubuntu-latest: 机器人用的是最新版的 Ubuntu Linux 系统。
  • python-version: ["3.10"]: 机器人会安装 Python 3.10 版本。
  • timeout-minutes: 10: 如果跑了 10 分钟还没完，强制停止（防止死循环浪费资源）。

✅ Task 5: 搞懂“具体干活步骤” (对应 steps: 部分)

目标：这是最关键的一步，看机器人具体敲了什么命令。

我把 steps 里的命令翻译成人类语言：

  1. Checkout:
    • 机器人把你的代码仓库下载下来。
  2. Set up Python:
    • 安装 Python 3.10。
  3. Install the current repository:
    • pip install -e .[test,prime,geo]: 安装你这个项目（Verl）本身，顺便把测试需要的工具（test）、核心组件（prime）和地理组件（geo）都装上。
    • pip install --upgrade "ray>=2.40.0" pillow: 额外升级 ray 和安装 pillow 这两个库。
  4. Running CPU unit tests (重头戏):
    • git clone ... verl-data: 如果没有数据，去下载测试用的数据集。
    • python3 examples/data_preprocess/geo3k.py: 运行一个数据预处理脚本，准备好数据。
    • 关键配置: bash echo '[pytest]' > pytest.ini echo 'python_files = *_on_cpu.py' >> pytest.ini 这两句命令临时创建了一个配置文件。它告诉测试工具 pytest：“只许跑文件名是 *_on_cpu.py 的文件，别的不要管！”
    • pytest -s -x tests/: 最后，启动测试工具扫描 tests/ 文件夹。
      • -s: 显示打印的日志。
      • -x: 一旦遇到 1 个错误，立刻停止（Fail fast）。

总结 (Summary)

这个文件到底讲了啥？

它定义了一个只能在 CPU 上运行的自动化测试流程。

它的逻辑是： 只要有代码更新 -> 启动一台 Ubuntu 电脑 -> 装好 Python 和依赖 -> 下载数据 -> 配置测试工具只筛选出名字带 _on_cpu 的文件 -> 开始测试 -> 如果有错就报错，没错就打勾通过。
