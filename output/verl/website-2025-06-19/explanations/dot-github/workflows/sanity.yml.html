.github/workflows/sanity.yml

这份文件其实包含了两部分内容：上半部分是“说明书”（给人看的注释），下半部分是“指令清单”（给机器执行的代码）。

简单来说，这是一个 GitHub Actions 的自动化脚本。它的作用就像一个严厉的图书管理员，每当你（或者别人）往代码库里提交新代码时，它就会跳出来，按照清单检查一遍，确保你没有把书架弄乱，也没有写错别字。

为了让你更容易理解，我把你当作这个项目的“新管理员”，列一个 Task Todo List (任务清单)，带你一步步看懂这个文件在干嘛。

🚀 新管理员的任务清单 (Task Todo List)

我们将这个文件的解读分为三个阶段： 1. 阶段一：阅读入职手册（看懂文件开头的注释） 2. 阶段二：设定安保规则（看懂什么时候触发检查） 3. 阶段三：执行例行检查（看懂具体检查了哪些内容）

阶段一：阅读入职手册 (理解测试分类)

文件最开头（# 开头的绿色注释部分）是写给开发者看的“地图”。

  • Task 1: 搞清楚测试文件放哪儿

    • 这个项目把测试代码都放在 tests/ 文件夹下。
    • 如果是测训练功能的，去 tests/trainer。
    • 如果是测模型的，去 tests/models。

  • Task 2: 识别“特殊”测试区 (Special Zones)

    • 有些测试比较特殊，放在以 special_ 开头的文件夹里：
      • special_distributed: 需要多张显卡一起跑的测试。
      • special_sanity: 重点！ 快速的“神智清醒”检查（就是当前这个文件要跑的）。
      • special_npu: 专门给 NPU 芯片跑的测试。

  • Task 3: 搞清楚用 CPU 还是 GPU

    • 默认规则：大部分测试默认都要用 GPU（显卡）。
    • 例外规则：如果文件名以 _on_cpu.py 结尾，或者在 special_npu 里，就不需要标准 GPU。

  • Task 4: 了解还有哪些其他的自动化检查

    • 注释里还列出了其他的 .yml 文件（比如 model.yml, e2e_*.yml），告诉你这个项目除了当前这个“基础检查”，还有“重型测试”、“端到端测试”等。

阶段二：设定安保规则 (Workflow Configuration)

从 name: sanity 开始，就是给 GitHub 机器人下达的指令了。

  • Task 5: 设定机器人的名字

    • name: sanity -> 这个机器人的代号叫“Sanity”（意为：神智清醒/健全性检查）。它的目的是确保代码最起码是“正常”的，没有犯低级错误。

  • Task 6: 设定“报警”触发器 (on:)

    • 什么时候启动？
      • 当有人 push (推送) 代码时。
      • 当有人提 pull_request (合并请求) 时。
    • 限制条件：
      • 只针对 main 分支或 v0.* 版本分支。
      • 且 修改了 .py 文件，或者修改了本配置文件，或者修改了 tests/special_sanity 下的文件。（如果只改了 README 文档，这个机器人可能就不理你了，为了省电）。

  • Task 7: 设定并发规则 (concurrency)

    • 如果你连续提交了两次代码，机器人会取消第一次还没跑完的任务，只跑最新的那次。这叫“别浪费资源，我只验最新的”。

阶段三：执行例行检查 (Jobs & Steps)

这是最核心的部分，机器人领命后，具体要在 Ubuntu 系统上干哪些活。

  • Task 8: 准备工作环境

    • runs-on: ubuntu-latest: 给我开一台最新的 Linux 电脑。
    • Set up Python: 安装 Python 3.10。
    • Install the current repository: 把当前项目的代码安装好（pip install ...）。

  • Task 9: 核心检查项 (一步步过安检) 这是机器人拿着放大镜在这个项目里查的东西：

    1. Run sanity test (跑基础测试)
      • 执行 pytest tests/special_sanity。这是最基本的测试集，如果这个都挂了，说明代码完全不能用。
    2. Run license test (查版权声明)
      • 检查代码文件里是不是都乖乖写了版权声明（License header）。
    3. Assert naming convention (查大小写拼写)
      • grep ... 'veRL'：全项目搜索。
      • 规定：项目名字必须叫 verl，不能写成 veRL。如果发现了 veRL，机器人直接报错退出，并大喊：“请使用 verl！”
    4. Validate test folder structure (查文件夹结构)
      • 运行一个脚本，确保你没有把测试文件乱放，必须符合阶段一里的目录规则。
    5. Assert documentation requirement (查文档)
      • 检查函数是不是都写了文档字符串（Docstring），没写的打手板。
    6. Assert device api usage (查硬件代码规范)
      • 分别检查 recipe 和 verl 文件夹。
      • 这通常是为了确保代码没有把硬件写死（比如直接写死 cuda），而是用了通用的接口，方便以后支持其他硬件。

总结

这个文件讲了啥？ 它定义了一个“代码门卫”。

它的观点（逻辑）是： 在跑那些耗时几小时的复杂模型训练测试之前，我们要先花 5分钟（timeout-minutes: 5）跑一遍这个 Sanity Check。如果连文件夹结构、命名规范、版权声明、基础导入都能出错，那就别浪费时间跑后面的大测试了，直接打回去重写。
