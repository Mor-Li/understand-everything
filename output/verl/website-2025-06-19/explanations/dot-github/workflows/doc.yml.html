.github/workflows/doc.yml

这份文件确实看起来有点“杂”，因为它其实包含了两个完全不同的部分： 1. 上半部分（注释）：是给程序员看的“说明书”，解释整个项目的测试（Test）文件该怎么放、怎么跑。 2. 下半部分（YAML代码）：是给 GitHub 机器人看的“指令”，专门用来测试文档（Documentation）能否正常生成。

为了让你看懂，我把它拆解成一个 “新员工入职任务清单” (Onboarding To-Do List)。你只需要跟着这个清单，一步步勾选，就能理解它的逻辑。

任务清单：理解 doc.yml

✅ 第一阶段：阅读“员工手册”（文件上半部分的注释）

这部分全是 # 开头的文字，机器不执行，是写给你看的。它告诉你这个项目里的测试文件是怎么分类的。

  • Task 1.1：搞懂文件夹结构

    • [ ] 规则：tests/ 下的文件夹对应代码里的模块。
      • 比如：tests/trainer 里的测试代码，就是专门测 verl/trainer 功能的。
    • [ ] 特殊区：看到 special_ 开头的文件夹要注意：
      • special_distributed：必须多张显卡才能跑。
      • special_e2e：端到端测试（从头跑到尾的完整流程）。
      • special_npu：给 NPU（另一种芯片）用的。

  • Task 1.2：搞懂硬件分配（CPU vs GPU）

    • [ ] 默认规则：除非特殊说明，测试默认都在 GPU 上跑。
    • [ ] 例外规则：如果你想在 CPU 上跑测试，文件名必须以 _on_cpu.py 结尾（比如 test_data_on_cpu.py）。

  • Task 1.3：搞懂自动化流程（Workflow）

    • [ ] 分类：GitHub 上有很多自动化任务：
      • 必做题（Sanity tests）：比如检查标题、查毒、检查文档（就是本文档 doc.yml 负责的）。
      • 大题（Heavy tests）：多卡测试，跑得慢。
      • 单元测试（Unit tests）：分 CPU 版和 GPU 版。

✅ 第二阶段：审查“文档机器人”的工作流程（文件下半部分的代码）

从 name: doc_test 开始，就是真正的代码了。这是告诉 GitHub 只要有人提交代码，就启动一个机器人来检查文档。

  • Task 2.1：确认机器人的启动时机 (on)

    • [ ] 什么情况触发？
      • 有人 push（推送）代码到 main 分支或 v0.* 版本分支时。
      • 有人提 pull_request（合并请求）时。
    • [ ] 为了省钱/省资源，哪些文件变了才触发？ (paths)
      • 只有当 .py (Python代码)、docs/** (文档文件) 或这个 doc.yml 变动时才跑。如果只是改了个 .txt 或图片，机器人就偷懒不跑了。

  • Task 2.2：配置机器人的工作环境 (jobs)

    • [ ] 操作系统：ubuntu-latest (最新的 Linux 系统)。
    • [ ] Python版本：3.10。
    • [ ] 超时限制：5分钟。如果 5 分钟还没跑完，直接强制停止（防止死循环浪费资源）。

  • Task 2.3：机器人的具体执行步骤 (steps)

    • 这是最核心的部分，机器人会按顺序执行以下命令：
    • [ ] 第一步：下载代码 (Checkout)
      • 把你的仓库代码拉取到机器人的环境里。
    • [ ] 第二步：装环境 (Install)
      • pip install -e .[test]：安装这个项目本身及测试依赖。
      • pip install -r docs/requirements-docs.txt：安装生成文档需要的工具（比如 Sphinx）。
    • [ ] 第三步：生成文档并找茬 (Run doc make html)
      • make clean：清理旧垃圾。
      • make html ...：尝试把文档源码编译成 HTML 网页。
    • [ ] 第四步：质检（关键！）
      • 查错：如果日志里出现 ERROR，机器人报错退出（测试失败）。
      • 查漏：如果日志里出现 WARNING: document isn't included in any toctree，说明你新写了一个文档文件，但忘记把它加到目录里了。机器人会报错并提醒你修改。

总结：这个文件到底是干嘛的？

简单来说，这个文件就是一个 “文档保洁阿姨”。

  1. 上半部分是贴在墙上的值日表（告诉大家测试文件该放哪、怎么命名）。
  2. 下半部分是阿姨的工作守则：每当有人改了代码或文档，她就跑出来，试着把文档打印一遍。如果打印过程中报错了，或者发现有页面没装订进目录，她就大喊一声“测试失败”，不让你合并代码。
