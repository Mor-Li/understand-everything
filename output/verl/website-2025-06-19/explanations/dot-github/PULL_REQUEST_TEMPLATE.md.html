.github/PULL_REQUEST_TEMPLATE.md

这份文件其实不是代码，而是一张“交作业的答题卡”（Pull Request Template）。

当你想给这个开源项目（Verl）贡献代码时，你必须按照这个模板填写内容，哪怕你代码写得再好，如果这张“答题卡”没填对，管理员大概率不会看你的代码。

为了让你更容易理解，我把你提交代码前要做的事情整理成了一个 5步走的 To-Do List。

📝 提交代码任务清单 (To-Do List)

✅ 第一步：起个符合规范的标题 (Title)

任务： 你的 PR（Pull Request，即代码提交申请）标题必须严格遵守格式。 原文对应： Checklist Before Starting -> Checked PR Title format

  • 格式公式： [模块名] 类型: 标题内容
  • 怎么填：
    1. 模块名 (modules)：必须从文件里列出的单词里选（比如 fsdp, megatron, model, doc 等）。如果你改了多个地方，可以用逗号隔开，比如 [megatron, doc]。
    2. 类型 (type)：必须从这 5 个词里选：
      • feat (新功能)
      • fix (修Bug)
      • refactor (重构代码，不改功能)
      • chore (杂活，比如改配置)
      • test (增加测试)
    3. 标题内容：简单写你干了啥。
  • 正确例子： [model] feat: Add Llama3 support (在 model 模块增加了 Llama3 的支持)
  • 错误例子： Fix bug (没模块，没类型，太模糊)

✅ 第二步：解释你干了什么 (Description)

任务： 像写周报一样，汇报你的工作内容。 原文对应： What does this PR do?, High-Level Design, Specific Changes

  • 一句话总结 (What does this PR do?)：简单概括。比如：“这个 PR 修复了训练时内存溢出的问题。” 如果有相关的 GitHub Issue，记得贴链接。
  • 设计思路 (High-Level Design)：如果你改动很大（比如加了新算法），要讲讲你的架构设计思路。如果是小改动，这部分可以略过。
  • 具体改动 (Specific Changes)：列出清单，比如“修改了 A 文件，删除了 B 函数，新增了 C 参数”。

✅ 第三步：拿出证据证明代码能跑 (Test)

任务： 展示测试结果，证明你的代码没把项目搞崩。 原文对应： Test

  • 如果 CI 能测：项目里有自动测试机器人（CI），如果它全绿了，你就在这里写“Passed CI”。
  • 如果 CI 测不了：比如你加了个新算法，机器人不懂。你需要自己跑实验，然后把训练曲线图、评估结果截图贴在这里。这是为了证明你的代码是真的有效的。

✅ 第三步半：教别人怎么用 (Docs & Usage)

任务： 如果你改了接口或者加了新功能，得告诉别人怎么用。 原文对应： API, Usage Example

  • API 变动：如果你改了函数的参数（比如原来只需传 a，现在要传 a 和 b），必须在这里说明。
  • 代码示例：在 Usage Example 下面贴一段 Python 代码，演示新功能怎么跑。这非常重要，方便审核人快速上手。

✅ 第四步：提交前的自我检查 (Pre-submit Check)

任务： 最后过一遍安检，打钩确认。 原文对应： Checklist Before Submitting

你需要确认做了以下事情（在方框里打 x）： 1. 读了指南：看过 Contribute Guide（贡献指南）了吗？ 2. 代码格式化：运行过 pre-commit 工具了吗？（用来自动把代码排版整齐的工具）。 3. 破坏性更新：如果你的修改会导致别人的旧代码跑不通，标题里要加 [BREAKING]。 4. 更新文档：代码改了，说明书（docs 文件夹里的文件）改了吗？ 5. 单元测试： * 加了新功能？-> 写新的测试代码覆盖它。 * 改了旧功能？-> 确保旧的测试代码还能跑通。

总结

简单来说，这个文件就是告诉你： “别直接把代码甩过来。请先把标题起对，然后写清楚你改了啥，贴出测试通过的截图，给个使用案例，最后检查一遍格式再提交。”
