nanovllm/engine/model_runner.py

这份代码确实涉及了很多大模型推理（Inference）的核心底层技术，包括分布式推理、显存管理（PagedAttention）、CUDA Graph 优化等。如果没接触过底层框架，看不懂是很正常的。

你可以把 ModelRunner 想象成一个“大模型的高级司机”。它的工作不仅是踩油门（运行模型），还要负责给车加油（管理显存）、协调车队（多卡通信）以及规划路线（预处理数据）。

为了让你读懂，我制定了一个 6步走的 Task List，我们按照这个顺序，一步步拆解这个文件在干什么。

📋 Task List：拆解 ModelRunner

  1. Task 1: 启动与组队 (Initialization & Distributed Setup)
    • 目标：加载模型权重，如果是多张显卡，要建立通信连接。
  2. Task 2: 圈地盘 (KV Cache Allocation)
    • 目标：计算显存，提前把存放“记忆（KV Cache）”的空间划分好，避免运行时频繁申请内存。
  3. Task 3: 准备食材 (Data Preparation - Prefill & Decode)
    • 目标：把人类的文本（Sequence）转换成模型能吃进去的 Tensor（包括 Input IDs, Positions 和内存地址映射）。
  4. Task 4: 抄近道 (CUDA Graph Capture)
    • 目标：对于重复性高的小任务（解码阶段），录制 GPU 指令，以后直接回放，极大提升速度。
  5. Task 5: 开车 (Execution Loop)
    • 目标：实际执行模型的前向传播（Forward Pass）并采样出下一个 token。
  6. Task 6: 传令兵 (Inter-Process Communication)
    • 目标：如果是多卡运行，主卡（Rank 0）如何通过共享内存指挥副卡同步干活。

逐步详细讲解

Task 1: 启动与组队 (Initialization)

对应代码： __init__ 方法

  • 你在看什么：
    • 代码首先初始化了分布式环境 (dist.init_process_group)。在大模型中，模型太大，一张卡放不下或者算得慢，需要切分到多张卡（Tensor Parallelism）。
    • rank 是显卡的编号，world_size 是总卡数。
    • load_model 把模型权重加载进显存。
    • warmup_model：先空跑一下模型，防止第一次运行时因为初始化各种库导致卡顿。

Task 2: 圈地盘 (KV Cache Allocation)

对应代码： allocate_kv_cache 方法

  • 核心概念：
    • 大模型在生成文本时，需要记住之前生成过的 token 的 Key 和 Value 矩阵，这叫 KV Cache。
    • 传统的做法很浪费显存。这里采用了类似 vLLM (PagedAttention) 的机制。
  • 代码逻辑：
    1. 查看当前显卡还有多少空闲显存 (torch.cuda.mem_get_info)。
    2. 计算一个“显存块 (Block)”有多大。
    3. 算出最多能塞下多少个块 (num_kvcache_blocks)。
    4. 一次性申请一个巨大的 Tensor self.kv_cache。
    5. 把这个大 Tensor 切分给模型的每一层 (module.k_cache = ...)。
    6. 比喻：你去图书馆自习，不是来一个人搬一把椅子，而是管理员根据剩余空间，直接划定一片区域全是座位，谁来了就往空位上坐。

Task 3: 准备食材 (Data Preparation)

对应代码： prepare_prefill 和 prepare_decode

  • 核心概念：
    • Prefill (预填充)：处理用户的 Prompt 阶段，一次性处理很多 token。
    • Decode (解码)：一个字一个字往外蹦的阶段。
  • 代码逻辑：
    • 模型不仅需要 input_ids (输入的字)，还需要知道这些字对应的 KV Cache 存在刚才申请的那个大内存池的哪里。
    • slot_mapping：这是关键。它告诉显卡：“第5个 token 的数据，请存到显存池的第 1024 号格子里”。
    • block_tables：记录每个句子占用了哪些内存块（Block）。
    • set_context：把这些元数据存到全局变量里，供模型层（Attention 层）使用。

Task 4: 抄近道 (CUDA Graph Capture)

对应代码： capture_cudagraph

  • 痛点：在 Decode 阶段，每次只处理 1 个 token，计算量很小。但是 Python 发送指令给 GPU 的开销很大（CPU overhead）。可能 CPU 发指令用了 10ms，GPU 算只用了 0.1ms。
  • 解决方案：
    • CUDA Graph 就像“录像机”。
    • 代码里针对不同的 Batch Size (1, 2, 4, 8...) 分别录制了一遍 GPU 的操作流程。
    • 以后运行时，只要 Batch Size 匹配，直接“播放录像”，跳过 Python 的指令发送过程。
  • 对应代码：run_model 里的 graph.replay() 就是在播放录像。

Task 5: 开车 (Execution)

对应代码： run 和 run_model

  • 流程：
    1. 准备数据：判断是 Prefill 还是 Decode，调用 Task 3 的函数准备数据。
    2. 运行模型：
      • 如果是 Prefill 或者大 Batch，直接跑 self.model(...)。
      • 如果是 Decode 小 Batch，使用 Task 4 的 CUDA Graph graph.replay() 加速。
    3. 采样 (Sampler)：模型输出的是概率（Logits），self.sampler 根据概率选出下一个 token ID。
    4. 返回：把生成的 token ID 返回给上层应用。

Task 6: 传令兵 (Inter-Process Communication)

对应代码： loop, read_shm, write_shm, call

  • 背景：如果是多卡运行（比如 2 张卡），Python 会启动 2 个进程。
    • Rank 0 (主进程)：负责接收外部请求，处理逻辑。
    • Rank 1+ (副进程)：傻傻地等着 Rank 0 给指令。
  • 机制：
    • 使用 SharedMemory (共享内存) 来传输指令。
    • Rank 0 调用 write_shm：把“函数名”和“参数”写进共享内存，然后触发 event.set() 通知大家。
    • Rank 1 运行 loop -> read_shm：一直死循环等信号。收到信号后，从内存读出“哦，主要让我运行 run 函数”，于是它就跟着运行。
    • 这就是为什么 Rank 0 算完 Sampler 拿到结果，而 Rank 1 不需要返回结果（它只是陪跑，负责算它那一半的矩阵乘法）。

总结

这个文件 model_runner.py 是一个极简版的高性能推理引擎核心。它去掉了 HuggingFace 那种臃肿的包装，直接操作底层：

  1. 自己管理内存（为了 PagedAttention）。
  2. 自己管理多进程通信（为了 Tensor Parallelism）。
  3. 自己优化执行路径（为了 CUDA Graph）。

如果你想看懂它，建议先从 run 方法入手，看它如何根据 is_prefill 分流，然后分别看 prepare_... 数据处理，最后看 allocate_kv_cache 理解内存是怎么管理的。
